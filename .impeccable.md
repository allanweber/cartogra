# Cartogra — Design Context

## Design Context

### Users

Mixed audience across three distinct personas who interact with the product differently:

- **Platform / infra engineers** — daily power users navigating service dependencies, tracking API contracts, investigating deployment history. They live in the tool and value density and speed.
- **SREs / oncall engineers** — situational users jumping in under pressure to understand blast radius, team ownership, and risk exposure. Every extra click costs them.
- **Tech leads / architects** — strategic users reviewing architecture health, team structure, and long-term risk trends. They need to present findings to stakeholders.

All three need the same thing from the UI: **immediate comprehension**. The data is complex; the interface must not be.

### Brand Personality

**Precise · Dependable · Insightful**

Cartogra is a trusted instrument panel. Like the best precision tools (a compass, an oscilloscope, a hydrographic chart), it never surprises you, never decorates for its own sake, and is instantly legible under pressure. The name echoes cartography — charting territory, mapping systems, navigating complexity.

### Emotional Goal

**Calm confidence** — "I can see everything, nothing surprises me."

The interface should feel like a control room that doesn't panic. Even when displaying critical risks or broken contracts, the UI itself communicates control. Color signals urgency; structure provides stability.

### Aesthetic Direction

**The precision instrument.** Think hydrographic charts, technical blueprints, professional cartography. Dense with information but never chaotic. Each element earns its place.

- **Not this**: Generic SaaS dashboards (DataDog clones, metric card grids), enterprise bloat (ServiceNow-style), startup playfulness (gradient everything, emoji in copy)
- **The right references**: Axiom, Hex, Linear (structure, not palette), professional instrument panels

**Brand color replacement**: The current primary (OKLCH hue 295, AI-startup violet) must be replaced. The replacement should read as a precision instrument — deep cartographic blue around **hue 215–225** (OKLCH). Something like `oklch(0.52 0.20 218)` for light mode, `oklch(0.72 0.16 218)` for dark mode. This hue sits in deep blue-teal territory: calm, authoritative, technical — and avoids every cliché (no AI purple, no emerald-green hero, no amber-brand).

**Semantic color system** (already established — keep exactly as-is):
- Green hue 145: healthy/deploy
- Amber hue 60: degraded/warning/ownership
- Red hue 28: down/critical/risk
- Blue hue 240: info/dependency
- Blue-violet hue 260: contract events

The brand accent (hue 218) is deliberately chosen to differ from all five semantic hues.

### Design Principles

1. **Data density over decoration** — Every pixel communicates. No decorative elements that don't carry information. When in doubt, remove it.
2. **Structural calm** — The layout itself signals control. Consistent grid, predictable patterns, no visual anxiety. The color encodes urgency; the structure stays composed.
3. **Progressive disclosure** — Start with what matters most, reveal detail through interaction. Primary views show health signals; drill-down surfaces root cause.
4. **Semantic color only** — Color carries meaning, never mood. The five semantic hues (health × severity × event type) are a system, not decoration. The brand accent should be used sparingly — primary actions, active states, focus rings.
5. **Expert density** — Target users are engineers who read terminals. Short labels, tight spacing, no hand-holding copy. Respect their attention. Empty states teach; they don't apologize.
