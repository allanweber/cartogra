## Video Outline: "I'm Building a Service Catalog Because Every Service Catalog Lies" (~6 min)

Format: screencast + talking-head segments. Terminal + browser demo in the middle.

---

### Segment 1 — Hook (0:00–0:30)

**On camera.**

Open the browser to a Confluence wiki page titled "Our Services." Scroll slowly. Count the entries — seventeen. Cut to terminal: `kubectl get pods -n production | wc -l` — 43.

"These numbers don't match. They haven't matched for months. Nobody knows exactly when they diverged."

No intro slide. No "hey welcome to my channel." The problem first.

---

### Segment 2 — The problem (0:30–2:00)

**Talking head, then screen share of a diagram.**

Explain the drift problem: manual catalogs require humans to remember to update them. Humans are bad at this under deadline pressure. New hires don't know about the wiki. Migrations lose entries.

Show a simple diagram: boxes for GitHub, K8s, OTel on one side. A wiki in the middle. Arrows showing "manual sync." Draw a red X through the arrows.

"This is not a discipline problem. It's an architecture problem. You're asking people to hand-copy something that already exists in your infrastructure."

Cost: incident responders trusting stale data. Blast-radius analysis missing services. New engineers onboarding to a map that doesn't match the territory.

---

### Segment 3 — The approach (2:00–3:30)

**Talking head + diagram.**

The alternative: derive the catalog from sources of truth.

Show updated diagram: GitHub + K8s + OTel arrows flowing *into* the catalog automatically. No manual step.

Key concepts to explain briefly:
- Auto-discovery from GitHub webhooks and Kubernetes watch
- Declared vs observed dependencies — OTel traces reveal what's actually calling what
- Drift detection: when observed ≠ declared, flag it as an event

"When the catalog is an index over real infrastructure signals, it doesn't drift. Deviations become detectable. They become alerts, not surprises."

Mention the temporal history angle: every state change is immutable history — you can query the graph as of any past date.

---

### Segment 4 — Demo (3:30–5:30)

**Screen share. Terminal + browser.**

1. `docker compose up` — show services coming up (gateway, registry, ingestion, Grafana)
2. Hit the health endpoint: `curl localhost:8080/actuator/health` — show the response envelope with `traceId`
3. Open Grafana (localhost:3000) — show the trace appearing. Click into it. Show service name, span names, timing.
4. Briefly show the Kafka consumer log — show `traceparent` header being extracted and continuing the trace.

"Every request that enters the system — HTTP, Kafka, gRPC — carries the same trace ID. You can follow any request end to end in Grafana without touching the application code."

Keep the demo tight. Don't explain every line. Show it working.

---

### Segment 5 — CTA (5:30–6:00)

**On camera.**

"Phase 0 is the foundation — gateway, registry, ingestion, observability. Phase 1 is the frontend: a service catalog UI with a live dependency graph.

Everything is in the repo — the code, the ADRs, the OpenAPI specs. Building entirely in public.

GitHub: github.com/allancassiano/cartogra. Subscribe if you want to follow Phase 1."
