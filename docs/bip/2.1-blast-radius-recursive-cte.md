## Blog Post (deep dive, ~1000 words)

**Title:** "If payments-api goes down, what breaks?" — One Recursive CTE

**Hook:** Every service catalog can draw the graph. Almost none can answer that question in one query. Ours is ~12 lines of SQL against a materialized view. The interesting part isn't the recursion — it's the three guards that stop it from running away.

**The query**

Downstream = "who is impacted if this service fails" = walk edges backwards (target → source):

```sql
WITH RECURSIVE traversal AS (
    SELECT :serviceId::uuid AS service_id, 0 AS depth, ARRAY[:serviceId::uuid] AS visited
    UNION ALL
    SELECT e.source_service_id, t.depth + 1, t.visited || e.source_service_id
    FROM dependency_graph_edges e
    JOIN traversal t ON t.service_id = e.target_service_id
    WHERE e.tenant_id = :tenantId
      AND t.depth < :maxDepthPlusOne
      AND NOT (e.source_service_id = ANY(t.visited))
)
SELECT service_id, MIN(depth) AS depth
FROM traversal
WHERE depth > 0
GROUP BY service_id
ORDER BY depth, service_id
```

Upstream ("what this depends on") is the same query with source/target swapped. Two constants, two strings — we chose duplication over a templated direction flag because each reads top to bottom.

**Guard 1 — cycle guard: the `visited` array**

Each row carries the path that got it there. `NOT (next = ANY(visited))` drops any step that revisits a node on *this path*. A 3-node cycle A→B→C→A terminates because the walk stops before returning to A. Acceptance test: a 3-node cycle terminates and returns exactly the other two nodes.

Honest caveat: this is a per-path guard, not a global visited set. In a dense DAG with many diamonds, the same node is reached via many distinct paths, so the CTE can enumerate path-count rows, not node-count rows. `MIN(depth) ... GROUP BY service_id` collapses them afterwards — but only after Postgres produced them. That's why guard 2 exists.

**Guard 2 — depth cap, with an off-by-one on purpose**

Default depth 3, max 6 (requests above 6 are clamped, not rejected). The SQL recurses to `maxDepth + 1`. That extra level isn't returned — it's counted. If anything exists at depth `maxDepth + 1`, the response sets `truncated: true` and `nodesBeyondDepth: N`. "Here's everything within 3 hops" and "…and there's more beyond that" are different answers; a silent cutoff would pass for the first while being the second.

**Guard 3 — node cap**

200 nodes per direction. Over the cap → trimmed, flagged with a separate truncation flag and `nodesBeyondCap`. Two independent flags because the user action differs: depth-truncated → raise depth; cap-truncated → the answer is "a lot", narrow it by other means.

**Why a materialized view, not the base table**

`dependency_graph_edges` is a flattened snapshot of live edges (`deleted_at IS NULL`), indexed on `(tenant_id, source_service_id)` and `(tenant_id, target_service_id)`. The traversal never re-filters soft deletes and never contends with the write path. Cost: reads are slightly stale (see the refresh post).

**Enrichment happens outside SQL**

SQL returns `(service_id, depth)`. Java then loads graph nodes (name, tier, owning team) in one batch lookup. Keeps the CTE about structure only.

**Numbers**

200-edge fixture, 133 nodes, local Ryzen 5 2600, Postgres 16, direct to the topology service: blast radius p95 **11.7 ms** (n=60 distinct start nodes, default depth). Full methodology and caveats in `docs/architecture/topology-performance.md` — this is a dev-box snapshot, not an SLO.

**Gotcha worth telling:** the naming trap. In the dependency list endpoint, "downstream" means "this service depends on." In blast radius, "downstream" means "who breaks if this fails." Both are individually right and they use the same word for opposite directions. We documented it on the class and test both; we did not "unify" them.

**CTA:** repo link; question — how does your catalog answer "what breaks?" today?

## LinkedIn Post (~350 words)

Every service catalog can draw you a dependency graph. Few can answer the question you actually ask at 2 a.m.: *if this service goes down, what breaks?*

In Cartogra it's one recursive CTE over a materialized view of live dependency edges. The recursion itself is the easy part. What makes it safe to expose as an API is three guards.

**Cycles.** Each traversal row carries the path it took. A step that revisits a node on its own path is dropped, so a 3-service cycle terminates and returns the other two. This is per-path, not global — in a dense graph it can enumerate more paths than there are nodes, which is exactly why the next guard exists.

**Depth.** Default 3 hops, max 6. The query deliberately recurses one level past the cap and *counts* what it finds there, so the response says "truncated, 4 more beyond this depth" instead of quietly pretending the answer is complete.

**Size.** A separate 200-node cap per direction, with its own flag — because "go deeper" and "this is simply large" call for different next steps.

On a 200-edge fixture the p95 is 11.7 ms on my dev machine, with the rest of the stack running. I've recorded the hardware and the caveats; it's a snapshot, not a promise.

The part I find most transferable: an honest "I stopped here" in the payload is worth more than a faster wrong answer.

When your tooling truncates a result, does it tell you?
