## Blog Post (600–1000 words)

**Title:** Here's What Cartogra Actually Looks Like (and the Full API Docs)

Build-in-public posts about architecture decisions are useful. Sometimes the most useful thing is
to show what the product actually does.

This post is that post. Here's a walk through the Cartogra catalog UI and pointers to the full
API surface for engineers who want to integrate programmatically.

**The catalog list**

The catalog home page (`/catalog`) is a dense list of all registered services for the tenant. The
design principle is information density — no card-grid with large whitespace, no hero banners. Each
row in the list renders:

- Service name (linked to the detail page)
- Health badge: `healthy` (green), `degraded` (amber), or `down` (red)
- Owner team name
- SCM provider badge (GitHub or Azure DevOps icon)
- Language/stack tag
- Last synced timestamp

The filter bar at the top is persistent: filter by team, health status, tech stack, SCM provider,
or free-text search. Filters are applied client-side against the loaded service list for
responsiveness. The `orphan` filter surfaces services with no registered team owner — a leading
indicator of catalog drift.

The list is virtualized via TanStack Table for tenants with hundreds of services. Empty states
are handled: "No services matched your filters" differs from "No services registered yet."

**The service detail page**

Navigating to `/catalog/{serviceId}` renders the full service record. Key sections:

- **Overview**: name, description, health status, language, deployment tier, custom metadata
- **Ownership**: team name linked to the teams page; last CODEOWNERS sync timestamp
- **SCM connection**: which connection sourced this service, repo URL, last sync result
- **OpenAPI contract**: link to the associated contract version (Phase 3); stub in Phase 1
- **History**: last 10 material changes from `service_history`, with change type and actor

The detail page is read-only in Phase 1. Editing is a Phase 3 feature tied to contract management.

**The auth screens**

The login page (`/login`) renders an email/password form and OAuth provider buttons (Google and
GitHub). The register page (`/register`) captures name, email, and password and triggers OTP
verification. The verify-email page (`/verify-email`) is a single field accepting the 6-digit
code. All auth state is managed in httpOnly cookies — no token visible in `localStorage`.

Error states surface the `traceId` from the API error envelope in an amber alert banner. A user
who encounters an auth error can report the trace ID to support and we can look up the exact
request in the observability pipeline.

**The SCM Connections settings page**

`/settings/scm-connections` lists registered SCM connections with their sync status, last sync
timestamp, and a health badge. The add-connection drawer is a two-step form: select provider,
then enter connection name and PAT/credentials. Deleting a connection requires a confirmation
dialog and soft-deletes the record — a subsequent sync will transition affected services to
`orphaned` status.

**The full API surface**

The implemented API is documented in two OpenAPI specs committed to the repository:

- **Gateway API** (auth, proxying, rate limiting): [`docs/api/gateway.openapi.yaml`](../../docs/api/gateway.openapi.yaml)
- **Registry API** (services, teams, SCM connections, history): [`docs/api/registry.openapi.yaml`](../../docs/api/registry.openapi.yaml)

Both specs use the shared response envelope component defined in `gateway.openapi.yaml`. Every
endpoint documents the `data` / `traceId` success shape, the `error` / `traceId` error shape,
and the `X-Trace-Id` response header. The `X-Tenant-Id` header is injected by the gateway and
forwarded to registry — it appears as a required header on registry endpoints but is set
automatically by the gateway for authenticated browser sessions.

Forward-looking specs for topology, contract, and intelligence are maintained as explicit stubs
in `docs/api/` with Phase ownership markers indicating when each endpoint will be implemented.

**What's next**

The dependency graph, contract hub, and intelligence panel are the Phase 2–4 features on the
roadmap. The catalog list in Phase 1 is the foundation they build on: a registry that stays
accurate because it reads from SCM truth instead of waiting for engineers to update it.

## LinkedIn Post (300–500 words)

**Title:** Six Months of Building in Public — Here's What Cartogra Looks Like Today

I've been documenting the architectural decisions behind Cartogra for several months: the
gateway-only auth pattern, the SCM sync pipeline, the multi-tenant data model. Today I want to
show what the product actually looks like from a user perspective.

**The catalog list**

The catalog home page renders every registered service with health status, owner team, SCM
provider source, and last sync timestamp. A persistent filter bar supports filtering by team,
health status, tech stack, and provider — plus a free-text search and an orphan filter that
surfaces services with no registered team owner. Orphan detection is a leading indicator of
catalog drift: a service that nobody owns is a service that won't get updated when its team
changes.

**The service detail**

The detail page shows an overview (name, tier, language, custom metadata), the team owner with
the last CODEOWNERS sync timestamp, the SCM connection that sourced the service, and an
append-only change history from the `service_history` table. The history table records every
material change with timestamp and actor — answering "what did this service look like three
months ago?" with a single database query.

**The full API surface**

The implemented API is published as OpenAPI specs in the repository:

- [Gateway API](../../docs/api/gateway.openapi.yaml) — auth routes, token issuance, rate limiting,
  proxying behaviour
- [Registry API](../../docs/api/registry.openapi.yaml) — service CRUD, team ownership, SCM
  connections, history queries

Both use a shared response envelope that includes a `traceId` in every response — success and
error alike. The trace ID is the same value as the W3C `traceparent` distributed trace
identifier, so a user-reported error trace ID immediately locates the request across the entire
observability pipeline.

**What's coming next**

Phase 2 brings the dependency graph: blast-radius analysis, cycle detection, observed-vs-declared
dependency views powered by OpenTelemetry span data. Phase 3 brings the contract hub: OpenAPI
compatibility checks, breaking-change detection, and CI integration.

For engineering leaders evaluating service registry options: what feature would you need to see
in a catalog before trusting it for blast-radius analysis during an incident?
