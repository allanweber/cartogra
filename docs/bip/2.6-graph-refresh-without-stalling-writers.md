## Blog Post (article, ~800 words)

**Title:** Three Small Things That Keep a Materialized View Fresh Without Hurting Writers

**Hook:** Graph queries need a flat, filtered, indexed copy of the edges. Postgres gives you one for free — and a refresh that, done naively, either blocks readers, runs 40 times per sync, or runs on every pod at once. We fixed each with about 30 lines.

**Why a view at all**

Blast radius, cycles and SPOF scoring all traverse edges. The base `dependencies` table carries soft-deletes, drift metadata and write-path churn. `dependency_graph_edges` is just `(tenant, source, target, type, protocol, metadata) WHERE deleted_at IS NULL`, with indexes in both traversal directions. Reads never think about `deleted_at`.

**Problem 1 — readers blocked during refresh → `CONCURRENTLY`**

Plain `REFRESH MATERIALIZED VIEW` takes an exclusive lock; every graph query waits. `REFRESH ... CONCURRENTLY` builds the new contents aside and swaps, so readers keep reading. Requirement: a unique index on the view — `(tenant_id, source, target, dependency_type, protocol)`. Cost: slower refresh, and Postgres computes a diff.

**Problem 2 — a sync writes 40 edges → debounce**

Mutations don't refresh. They call `markDirty()` — one `AtomicBoolean.set(true)`. A fixed-delay tick (default `PT5S`) checks the flag; if set, clear it and refresh once. A burst of 40 observed-edge upserts is one refresh. Writers pay nothing: no refresh, no lock, no wait.

Order matters: the flag is cleared *before* the refresh. A write landing mid-refresh re-sets it and gets the next tick. If the refresh throws, we set it back to dirty so the failure retries instead of vanishing.

**Problem 3 — N replicas all refreshing → advisory lock**

Scale topology horizontally and every instance has its own dirty flag and tick. Without coordination they all refresh at once, wasting work and fighting over the view. The tick does `tryAcquireLock(key)` — a non-blocking Postgres advisory lock. Not acquired → return, leave the flag set, try next tick. Held by someone else means a refresh is already running; ours would only redo it. Released in `finally`.

```java
if (!dirty.get()) return;
if (!lockRepository.tryAcquireLock(LOCK_KEY)) return;
try { dirty.set(false); graphViewRepository.refresh(); }
catch (Exception e) { dirty.set(true); log.error(...); }
finally { lockRepository.releaseLock(LOCK_KEY); }
```

**What it costs you (be upfront)**

- Reads are eventually consistent: worst case ≈ debounce interval + refresh time. A user who declares an edge may not see it in blast radius for ~5 s.
- The dirty flag is in-process. A write handled by pod A only marks A dirty. Fine here — A refreshes the shared view — but if A dies between write and tick, nothing marks it. Periodic reconciliation is not built; it's not in Phase 2.
- The lock key is global, not per-tenant: one tenant's churn refreshes everyone's view. Acceptable at current scale; first thing to revisit if the view gets big.

**Numbers**

200 edges, 133 nodes: refresh median **26.3 ms** (n=5, min 24.5 / max 33.9), local Ryzen 5 2600, Postgres 16, unconstrained container, other dev processes running. That's the SQL only — not the 5 s debounce. Refresh cost scales with total edges across all tenants, so this number is the optimistic end, not a forecast.

## LinkedIn Post (~320 words)

A dependency graph is only useful if it's fast to query — so we query a materialized view of live edges rather than the base table. The view needs refreshing, and the naive options all hurt.

Three small decisions in about 30 lines of Java:

**Refresh concurrently.** Plain refresh blocks every reader. `CONCURRENTLY` doesn't, provided the view has a unique index.

**Debounce.** Writers never refresh. They flip an in-process "dirty" flag; a 5-second tick does one refresh for however many writes arrived. A batch of 40 edge upserts costs one refresh and adds zero latency to the write.

**Coordinate with an advisory lock.** With multiple replicas each ticking independently, you'd refresh N times. A non-blocking `try` lock means "someone's already on it — skip."

The trade-offs are real and worth stating: reads can be up to ~5 seconds stale; the dirty flag is per-process, so a pod crashing between a write and its tick can miss a refresh (no reconciliation yet); and the lock is global rather than per-tenant.

Measured on a 200-edge fixture on a dev machine: 26 ms median refresh. Not a forecast for production scale — refresh cost grows with total edges.
