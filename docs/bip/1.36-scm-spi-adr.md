# BIP 1.36 — SCM Provider SPI ADR

## Blog Post (600–1000 words)

### How We Designed a Provider-Agnostic SCM Abstraction for Cartogra's Ingestion Layer

When building Cartogra's service registry, one of the earliest architectural forks we hit was: how do we ingest repository metadata from both GitHub and Azure DevOps without turning the ingestion service into a sprawling if-else tree?

The answer was a clean Service Provider Interface (SPI) — and this post walks through the decision, the design, and the tradeoffs we accepted.

**The Problem**

Cartogra's ingestion service needs to do three things across every SCM provider:
1. List repositories in an organization or project.
2. Fetch file contents (e.g. `CODEOWNERS`, OpenAPI specs, `service.yaml`).
3. Resolve team ownership from whatever the provider's native model is.

GitHub and Azure DevOps are structurally different. GitHub uses `CODEOWNERS` files and a flat org/repo model. Azure DevOps uses a hierarchical organization → project → repository tree, and ownership comes from Required Reviewers policies or custom `CODEOWNERS` files. Their auth models differ too: GitHub accepts PATs and GitHub Apps; Azure DevOps uses PATs or service principals.

A naive implementation would put all of this in one fat class. Adding GitLab later would mean forking that class again. We've seen this pattern age poorly.

**The SPI Design**

We defined a single Java interface in the ingestion service's `application/port/out` package — the hexagonal architecture's output port boundary:

```java
public interface ScmProvider {
    String providerType();
    List<ScmRepository> listRepositories(ScmConnectionConfig config);
    Optional<String> getFileContents(ScmConnectionConfig config, String repoPath, String filePath);
    OwnershipMap resolveOwnership(ScmConnectionConfig config, ScmRepository repository);
}
```

Key decisions baked into this signature:
- **`ScmConnectionConfig` is passed per-call**, not injected at construction. This means the ingestion worker doesn't hold credentials; it receives them per sync command from the registry's `scm_connections` table (stored as JSONB). Credentials never live in env vars on the ingestion side.
- **`Optional<String>` not `null`** — the project enforces `Optional` at all method return boundaries.
- **`OwnershipMap` is a plain record** — no framework dependencies. `shared:common` has zero Spring imports; the SPI types are also Spring-free.

**The Implementations**

`GitHubProvider` and `AzureDevOpsProvider` each live in their own sub-package under `infrastructure/scm/`. They create an internal REST client (`GitHubRestClient`, `AzureDevOpsRestClient`) per call, using the `apiBaseUrl` in the connection config — which lets WireMock-backed tests override the base URL without touching env vars.

Spring wires all `ScmProvider` beans into a `Map<String, ScmProvider>` keyed by `providerType()`:

```java
@Bean
public Map<String, ScmProvider> scmProviders(List<ScmProvider> providers) {
    return providers.stream()
            .collect(Collectors.toMap(ScmProvider::providerType, Function.identity()));
}
```

The use case dispatches by string: `providers.get(command.providerType())`. Adding GitLab means implementing `ScmProvider`, annotating with `@Component`, done.

**What We Explicitly Rejected**

- **Third-party VCS abstraction libraries** — there is no maintained Java library that covers GitHub PATs, GitHub Apps, Azure DevOps PATs, and Azure DevOps service principals with the exact API surface we need.
- **gRPC across providers** — deferred to Phase 6; would add complexity with no benefit for local HTTP calls.
- **Config stored in env vars** — this would couple the number of env vars to the number of connections per tenant. JSONB in Postgres scales to N connections without redeploying.

**The Tradeoff We Accepted**

Provider-specific config leaks into the generic `Map<String, Object> config` field. A misconfigured GitHub connection (missing `token` key) fails at runtime, not at startup. We mitigate this with `@Validated` config validation on the connection creation endpoint in the registry service, and clear error messages from `ScmProviderException`.

**Takeaway**

The SPI pattern keeps the ingestion pipeline entirely SCM-agnostic. The `ExecuteSyncUseCaseImpl` doesn't know what GitHub is — it only knows about `ScmProvider`. When we add GitLab in Phase 3, no use-case code changes.

## LinkedIn Post (300–500 words)

**The SCM provider decision that will save us months in Phase 3**

We're building Cartogra — a living service registry that ingests metadata from source-control systems. Last week we shipped the SCM provider abstraction layer. Here's the architectural decision that made it work cleanly.

**The challenge:** GitHub and Azure DevOps are both major SCM providers, but they have fundamentally different APIs, different auth models, and different ownership concepts. We needed to support both from day one — and not write ourselves into a corner before GitLab or Bitbucket become necessary.

**The solution:** A Spring-free `ScmProvider` SPI in the hexagonal output port boundary. Three methods: list repositories, get file contents, resolve ownership. Each provider implements it. The ingestion pipeline only knows about the interface.

The design decision I'm most proud of: credentials are passed per call through `ScmConnectionConfig`, sourced from JSONB stored in the registry's `scm_connections` table. We never store credentials as env vars on the ingestion service — that would require one env var set per connection per tenant. JSONB in Postgres scales to N connections without any deployment changes.

Spring collects all `@Component` `ScmProvider` beans into a `Map<String, ScmProvider>`. Adding a new provider means: implement the interface, annotate with `@Component`. The use case dispatches by string. No registration boilerplate.

Testing: WireMock-backed tests override the base URL via `apiBaseUrl` in the connection config. Tests run completely offline, in parallel, with no env mocking or test profiles.

We documented this in ADR-0002 in our repo. The decision captures what we rejected: third-party VCS abstraction libraries (none cover our auth surface), gRPC (deferred to Phase 6), and per-provider env vars (doesn't scale to multi-tenant).

**The outcome:** Phase 3 (GitLab support) will cost one interface implementation and one config class. No changes to the ingestion pipeline, no changes to the use case, no changes to the Kafka consumer.

Architectural decisions made early compound over time — in both directions.
