## Blog Post (600–1000 words)

**Title:** One Misconfigured Rate Limit Let Attackers Enumerate Usernames

**Hook:** Before we added rate limiting to Cartogra's auth endpoints, a script could try 1,000 email/password combinations in under a minute. Here's how we fixed it with Redis token buckets, per-tenant key isolation, and observable 429 responses — and how we test it without hitting a real Redis.

---

**Why auth endpoints are different**

Most rate limiting is about protecting infrastructure: preventing one user from overwhelming your database. Auth endpoint rate limiting is about protecting users: preventing credential stuffing, password spraying, and username enumeration.

Credential stuffing works by trying leaked password/email combos at scale. If your `/auth/login` endpoint doesn't rate limit, attackers can cycle through millions of combinations. If it returns different error messages for "wrong password" vs "user not found", they can enumerate which emails are registered.

Cartogra uses the same `INVALID_CREDENTIALS` error for both cases (wrong password and missing user), and applies stricter rate limits to all `/v1/auth/**` endpoints.

**Token buckets, not sliding windows**

Spring Cloud Gateway ships with a built-in `RedisRateLimiter` that implements the token bucket algorithm. A token bucket has two parameters:
- **replenish rate**: tokens added per second
- **burst capacity**: maximum tokens the bucket can hold

A burst of requests is allowed up to the capacity, then the bucket refills at the replenish rate. This is more forgiving than a sliding window (legitimate users can burst briefly) but still protects against sustained attacks.

Cartogra uses two configurations:

```yaml
# Auth endpoints — stricter
app:
  rate-limit:
    auth-replenish-rate: 5      # 5 requests/second sustained
    auth-burst-capacity: 10     # up to 10 before throttling kicks in

# All other routes — relaxed
    default-replenish-rate: 20
    default-burst-capacity: 40
```

**Per-IP key isolation**

The `KeyResolver` determines what to bucket on. Cartogra uses the client IP address:

```java
@Bean
public KeyResolver ipKeyResolver() {
    return exchange -> Mono.justOrEmpty(
        exchange.getRequest().getRemoteAddress()
    ).map(addr -> addr.getAddress().getHostAddress())
     .switchIfEmpty(Mono.just("unknown"));
}
```

Redis key format: `request_rate_limiter.{ip}.tokens` and `request_rate_limiter.{ip}.timestamp`. Different IPs get different buckets — a rate-limited attacker doesn't affect legitimate users behind a different IP.

**Observable 429 responses**

Spring Cloud Gateway's built-in rate limiter returns an empty 429 body by default. That's useless for debugging — clients get no `traceId`, no error code, no information about when to retry.

Cartogra overrides this with a custom `ErrorWebExceptionHandler` that wraps the 429 in the standard error envelope:

```json
{
  "error": {
    "code": "RATE_LIMITED",
    "message": "Too many requests — please slow down"
  },
  "traceId": "a3f1c8d2e4b5f6a7b8c9d0e1f2a3b4c5"
}
```

The `traceId` is always present, even on 429s. If a legitimate user gets rate limited, they can report the trace ID and you can see exactly which IP and endpoint triggered it in your observability stack.

**Testing without a real Redis**

Rate limit tests use Testcontainers with `com.redis:testcontainers-redis`. The `RateLimitIT` integration test:

1. Sends `authBurstCapacity + 1` requests to `POST /v1/auth/login` in rapid succession
2. Asserts the last response is HTTP 429
3. Asserts the 429 body contains `error.code = "RATE_LIMITED"` and a `traceId`
4. Asserts `X-RateLimit-Remaining` header is 0 on the throttled response

The test doesn't sleep between requests — it fires them fast enough to exhaust the burst capacity. The Redis Testcontainer provides real token-bucket semantics, unlike mocks that would pass even with broken Lua scripts.

**What about per-tenant rate limiting?**

IP-based limiting is the baseline. For multi-tenant SaaS, you might also want per-tenant limits (a high-volume tenant shouldn't exhaust the bucket for other tenants on the same IP, e.g., behind a corporate proxy).

Per-tenant limiting is a Phase 3 enhancement. The key change is the `KeyResolver`: swap `getRemoteAddress()` for `ReactiveSecurityContextHolder.getContext().map(ctx -> ctx.getAuthentication().getName())` on authenticated routes. The Redis key format becomes `request_rate_limiter.{tenantId}.tokens`, fully isolated per tenant.

## LinkedIn Post (300–500 words)

**Title:** How We Protected Cartogra's Auth Endpoints from Credential Stuffing

Credential stuffing is simple: attackers take leaked email/password combinations from data breaches and try them against your login endpoint. Without rate limiting, they can try thousands of combinations per minute.

In Cartogra (a multi-tenant service registry platform we're building in public), we added Redis token bucket rate limiting with a stricter configuration specifically for auth endpoints. Here's what we learned.

**Token buckets vs sliding windows**

We chose the token bucket algorithm (via Spring Cloud Gateway's built-in `RedisRateLimiter`) because it allows brief legitimate bursts without penalizing real users. A developer refreshing quickly while debugging gets through; a script cycling through thousands of passwords doesn't.

Auth endpoints get a tighter bucket (5 req/s, burst of 10). Everything else gets a more relaxed configuration (20 req/s, burst of 40).

**Observable errors, not empty responses**

Spring Cloud Gateway's default 429 response is an empty body. That makes debugging painful — a legitimate user who gets rate limited (behind a shared corporate IP, for example) gets no actionable information.

We override it with our standard error envelope:

```json
{
  "error": { "code": "RATE_LIMITED", "message": "Too many requests" },
  "traceId": "a3f1c8d2..."
}
```

Every 429 has a trace ID. If a legitimate user reports it, we can look up exactly what happened in our observability stack within seconds.

**Testing with real Redis**

Our `RateLimitIT` integration test uses Testcontainers Redis — not mocks. This matters: Spring Cloud Gateway's rate limiter runs a Lua script in Redis to atomically decrement the token bucket. A mock would bypass the script and the test would pass even if the configuration was wrong.

The test fires `burstCapacity + 1` requests rapidly, asserts the last response is 429, and verifies the error envelope contains the expected code and a trace ID.

**What's next**

Per-IP limiting is the baseline. Phase 3 will add per-tenant rate limiting for authenticated routes — so a high-volume tenant can't exhaust the bucket for other tenants sharing an IP (common in enterprise environments with shared corporate proxies).

The infrastructure for this is already in place: switching from IP-based to tenant-ID-based `KeyResolver` is a small change. The bucket isolation is real either way.

How does your team approach rate limiting on auth endpoints? Shared IP bucket, per-user bucket, or something else?
