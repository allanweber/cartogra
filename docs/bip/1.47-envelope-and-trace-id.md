## Blog Post (600–1000 words)

**Title:** Every API Response Carries a Trace ID — Here's Why, and How

The first time I lost 45 minutes debugging a production API error, the problem was simple: the
response said "something went wrong" and gave me nothing else. No request ID. No correlation.
Nothing to grep for in the logs.

That experience drove one early Cartogra decision: every API response carries a trace ID.
Not as an afterthought — as a first-class field in the response envelope.

**The envelope format**

Every response from every Cartogra service wraps its payload in a two-field envelope:

```json
{
  "data": { "id": "...", "name": "payment-service", ... },
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

Errors follow the same shape:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Service with id abc not found",
    "details": {}
  },
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

The `traceId` is always present, always a 32-character lowercase hex string — the OpenTelemetry
W3C trace ID format. The same value appears in the `X-Trace-Id` response header.

**Where the ID comes from**

Cartogra uses OpenTelemetry with Spring Boot's auto-instrumentation. Every inbound HTTP request
starts a new OTel span. Extracting the trace ID takes exactly one line:

```java
String traceId = Span.current().getSpanContext().getTraceId();
```

That ID is added to every response body and every response header. The log line for the same
request also carries `traceId` as a structured field. One ID, three places: body, header, log.

**Why the `X-Trace-Id` header duplicates the body**

Because API consumers often check headers before parsing JSON. A monitoring tool, a CDN, a test
assertion — all of them can read `X-Trace-Id` without deserializing the body. Duplicating it
costs nothing and makes a narrow class of integrations dramatically simpler.

The contract is enforced by test: `GatewayEnvelopeContractTest` and `RegistryEnvelopeContractTest`
assert that every response — 2xx and 4xx alike — has both fields, and that they match.

**What the traceId actually unlocks**

When a user files a support request, they paste the `traceId` from the error message the frontend
surfaced. We grep for it in the LGTM/Loki log pipeline. Every log line from gateway → registry →
topology that participated in that request carries the same ID. The entire call graph for that
one request is instantly visible — no log archaeology, no timeline stitching.

For the platform team, the trace goes further: the same ID connects to the Tempo distributed
trace, showing exactly which span was slow or failed and what the downstream service returned.

**The W3C `traceparent` header propagates it downstream**

The gateway doesn't just add the ID to the response — it propagates it forward. Every
`RestClient` call to a downstream service includes the W3C `traceparent` header:

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

Every Kafka message includes it as a message header. OTel auto-instrumentation picks it up on
the receiving end and continues the same trace. One request, one ID, across every hop.

**The anti-pattern this avoids**

The alternative — returning a raw response body without an ID — forces every debugging session
to rely on approximate log timestamps. "The error happened around 14:32" leads to "grep for
that path around that time" which leads to "which of these fifteen requests was it?" The envelope
eliminates that class of question entirely.

If you're building an API and you're not including a correlation ID in every response, add it
now. The implementation is four lines. The operational return is significant.

## LinkedIn Post (300–500 words)

**Title:** The four-line API change that made production debugging 10× faster

When building Cartogra, a living service registry for engineering teams, one of the earliest
decisions we made was deceptively simple: every API response, success or error, carries a trace
ID in the body and in a response header.

It looks like this:

```json
{
  "data": { "id": "...", "name": "payment-service" },
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

The `traceId` is the OpenTelemetry W3C trace ID for the request — a 32-character hex string that
identifies every log line, every downstream service call, and every Kafka message that
participated in handling that one request. The same value appears in the `X-Trace-Id` response
header.

**Why both places?**

Response headers are readable without deserialising the body. Monitoring tools, CDNs, and test
harnesses can check compliance without touching JSON. Duplicating the ID costs nothing and makes
a category of integrations simpler.

**The operational payoff**

When a user encounters an error, the frontend surfaces the `traceId` in the error message. The
user includes it in a support request. We search our log aggregation pipeline for that exact
string. Every log line across gateway, registry, and topology — for that one request — comes
back immediately. No timestamp correlation. No guessing which of fifty concurrent requests
failed. One search, one trace, complete picture.

For engineers on call, it goes further: the same ID connects to the distributed trace in Tempo,
showing which span was slow, what the downstream service returned, and where in the call chain
the error originated.

**The propagation piece**

The ID doesn't stop at the first service. Every outbound `RestClient` call includes the W3C
`traceparent` header. Every Kafka message includes it as a message header. OpenTelemetry
auto-instrumentation picks it up on the receiving end and continues the same trace. One request,
one identifier, visible across the entire system.

This is one of those decisions that looks obvious in hindsight but is easy to skip when you're
moving fast. Adding it later means retrofitting every controller, every error handler, every
test assertion. Adding it first — as an architectural constraint — means it's simply always
there.

If you're building a multi-service API and correlation IDs aren't part of your response contract,
what's the tipping point that would make you add them?
