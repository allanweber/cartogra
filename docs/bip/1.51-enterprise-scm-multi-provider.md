## Blog Post (600–1000 words)

**Title:** One Registry for GitHub Teams and Azure DevOps Teams — No Compromises

Enterprise engineering organisations rarely use one SCM. Acquisitions bring different toolchains.
Separate business units standardised on different providers. A founding team that preferred GitHub
acquired by a company standardised on Azure DevOps. The result: two SCM environments, two siloed
service registries, and an ops team that owns services in both without a unified view.

Cartogra's answer is a `ScmProvider` SPI that makes the registry provider-agnostic by design.

**The provider problem**

A service registry that only talks to GitHub is not an enterprise-grade catalog. The GitHub
provider knows how to list repos, fetch `service.yaml`, read `CODEOWNERS`, and register org-level
webhooks. The Azure DevOps provider knows how to list repos across a project collection, read the
same files from a different path hierarchy, and register Azure DevOps service hooks. Their APIs,
authentication models, and webhook semantics are completely different.

The naive approach — branching on provider type inside the sync logic — creates a maintenance
burden that grows with every provider added. Change the sync algorithm once, test it for both
providers, ship it once.

**The ScmProvider SPI**

Cartogra's ingestion service defines a Spring-free interface:

```java
public interface ScmProvider {
    String providerType();
    List<ScmRepository> listRepositories(ScmConnectionConfig config);
    Optional<String> getFileContents(ScmConnectionConfig config, String repo, String path);
    OwnershipMap resolveOwnership(ScmConnectionConfig config, ScmRepository repository);
    void registerWebhook(ScmConnectionConfig config, String targetUrl);
    void deregisterWebhook(ScmConnectionConfig config, String externalWebhookId);
    boolean verifyWebhookSignature(ServerHttpRequest request, byte[] rawBody, ScmConnectionConfig config);
    boolean isRelevantWebhookEvent(ServerHttpRequest request);
}
```

`GitHubProvider` implements it using GitHub's REST API with PAT or GitHub App credentials.
`AzureDevOpsProvider` implements it using Azure DevOps REST APIs with PAT or service-principal
credentials. The sync use case dispatches by `providerType` string — it contains no
provider-specific code.

Credentials are not environment variables. They live in the `scm_connections` table as JSONB,
scoped per tenant per connection. A single Cartogra tenant can have five GitHub connections for
five different organisations and two Azure DevOps connections for two business units — all
syncing in parallel, all with their own credentials and webhook registrations.

**What shows up in the catalog**

Once both providers are synced, the catalog list page renders services from both SCM sources
side by side. The SCM provider badge on each service card shows the source (GitHub mark or Azure
DevOps mark). The detail page shows which connection the service was discovered from, when it was
last synced, and the current sync health.

CODEOWNERS ownership mapping works across both providers. The ownership resolution algorithm is
identical — it reads the parsed `OwnershipMap` from whichever provider produced it and applies
the ADR-0015 matching rule (single unambiguous team match → set `services.team_id`). The sync
use case doesn't need to know whether the CODEOWNERS came from GitHub or Azure DevOps.

**Why this matters for enterprise teams**

A registry that forces you to pick one SCM provider creates a catalog blind spot for everything
on the other provider. Worse, it incentivises teams to maintain parallel registries — one per
provider — which is the problem a registry is supposed to solve.

With provider-agnostic sync, the catalog reflects the complete service estate. SREs looking at
blast radius analysis see dependencies across both provider-sourced services. Tech leads doing
architecture reviews see the full picture. The question "which services don't have a registered
owner?" is answerable across the entire tenant, not just the GitHub half of it.

Adding GitLab, Bitbucket, or an internal Gitea instance in the future requires implementing one
interface. The sync pipeline, ownership resolution, webhook controller, and catalog API are
unchanged.

## LinkedIn Post (300–500 words)

**Title:** Why Your Service Registry Should Be SCM-Agnostic — and How We Built That in Cartogra

Enterprise engineering organisations rarely standardise on a single source control provider.
Acquisitions bring different toolchains. Teams that grew organically made different choices.
A startup built on GitHub gets acquired by an organisation standardised on Azure DevOps. The
result is a mixed SCM estate — and most service registries are not built for it.

In Cartogra (a multi-tenant service registry platform we're building in public), we addressed
this with a `ScmProvider` interface in the ingestion service. `GitHubProvider` and
`AzureDevOpsProvider` implement it. The sync algorithm, webhook routing, and CODEOWNERS ownership
resolution are all provider-agnostic — they dispatch to the correct implementation by provider
type string and never contain provider-specific logic.

**What this means in practice**

Credentials are stored per-connection in the database as JSONB, not as global environment
variables. A tenant can have three GitHub organisation connections and two Azure DevOps project
connections active simultaneously, each with its own PAT or service-principal credentials and
webhook registration.

The catalog list renders services from all connections side by side, with a provider badge on
each card. CODEOWNERS ownership mapping applies the same resolution algorithm regardless of
provider. Blast-radius analysis and dependency graphs include services from all registered
sources — no "GitHub-only" blind spot.

**The extensibility outcome**

Adding GitLab, Bitbucket, or an internal Gitea instance in the future requires implementing the
`ScmProvider` interface — approximately 300 lines for a new provider. The sync pipeline, webhook
controller, ownership resolution, and catalog API are unchanged.

This design pays for itself the first time you inherit an acquisition's service estate. The new
organisation's Azure DevOps project becomes another connection in the same tenant. Their services
appear in the same catalog, owned by the same teams (or flagged as unmatched for manual
assignment), visible in the same dependency graph.

A registry with a provider lock-in creates a second catalog for the other half of the estate.
A registry designed around a provider SPI doesn't.

For engineering leaders managing mixed SCM environments: what's been the biggest barrier to
getting a unified view of your service estate? Provider support, ownership model, or something
else?
