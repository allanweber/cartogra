## Blog Post (600–1000 words)

**Title:** Your Auth Lives in the Gateway — Not the Service

**Hook:** Most Spring microservice tutorials show you how to add `spring-boot-starter-security` to every service. That's a trap. Here's how Cartogra puts auth exactly once — in the gateway — and why browser clients and API clients get the same security from two different transport mechanisms.

---

**The problem with per-service auth**

When every service validates tokens independently, you end up with:
- Duplicate JWT validation logic scattered across 5+ services
- Key rotation requiring a coordinated deploy of every service at once
- No single place to enforce rate limits before credentials are checked
- Inconsistent behavior when one service's version of the secret drifts

The fix is straightforward: one issuer, one validator.

**The gateway as the perimeter**

In Cartogra, the `gateway` service (port 8080) is the *only* component that issues and validates JWTs. Registry, topology, contract — none of them touch a token. They receive `X-Tenant-Id` and `X-User-Id` headers injected by the gateway's `TenantInjectionGlobalFilter` after the JWT is validated.

This is enforced architecturally: backend services accept those headers only from the gateway, never from external callers. (In production, K8s NetworkPolicy and a short-lived `X-Gateway-Token` add a second enforcement layer.)

**Dual-mode: same token, two transports**

Browsers and API clients have different constraints:

- **Browsers** can't easily set `Authorization: Bearer` headers on plain `<a>` links, form submits, or redirects. But they *can* automatically attach cookies. Cookies with `HttpOnly; Secure; SameSite=Lax` are inaccessible to JavaScript — XSS cannot steal them.
- **API clients** (CI pipelines, CLI tools) can't handle cookies. They need a raw token they can put in an `Authorization` header.

The solution is to issue the same JWT and deliver it both ways on login:

```java
// AuthController.java — login response sets both
if (tokens.accessToken() != null) {
    response.addCookie(ResponseCookie.from("jwt", tokens.accessToken())
        .httpOnly(true).secure(true).sameSite("Lax").path("/")
        .maxAge(tokens.expiresIn()).build());
}
// Body also contains access_token for API clients
return Mono.just(ResponseEntity.ok().body(new ApiResponse<>(tokens, traceId)));
```

The `JwtAuthenticationWebFilter` tries both extraction paths in order:

```java
private Mono<String> extractRawToken(ServerWebExchange exchange) {
    HttpCookie cookie = exchange.getRequest().getCookies().getFirst("jwt");
    if (cookie != null) return Mono.just(cookie.getValue());

    String bearer = exchange.getRequest().getHeaders().getFirst(HttpHeaders.AUTHORIZATION);
    if (bearer != null && bearer.startsWith("Bearer ")) {
        return Mono.just(bearer.substring(7));
    }
    return Mono.empty();
}
```

Cookie takes precedence — if both are present, the cookie wins. This matches browser behavior (cookies are automatic) without penalizing API clients.

**Tenant identity comes from the token, never the client**

A critical security invariant: `X-Tenant-Id` from inbound client requests is always stripped and replaced with the value from the validated JWT. A client cannot forge their tenant ID, even with a valid token for a different tenant.

```java
// TenantInjectionGlobalFilter.java
ServerHttpRequest stripped = exchange.getRequest().mutate()
    .headers(h -> {
        h.remove("X-Tenant-Id");
        h.remove("X-User-Id");
    })
    .build();
```

This runs on every request, authenticated or not. Backend services receive headers they can trust unconditionally.

**Reactive WebFlux, blocking JDBC**

The gateway is Spring WebFlux, but the user/token lookups use Spring Data JDBC — which is blocking. This is fine because `spring.threads.virtual.enabled=true` means every JDBC call runs on a virtual thread. No pinning, no starvation, no reactor operator wrapping needed for the happy path.

For JWT decode in the auth filter, the call is wrapped in `Mono.fromCallable(() -> decoder.decode(token))` — the Nimbus decode is CPU-bound and completes in microseconds.

## LinkedIn Post (300–500 words)

**Title:** Why We Put Auth in the API Gateway (and Nowhere Else)

The conventional wisdom for Spring microservices is to add `spring-boot-starter-security` and JWT validation to every service. It works. But it creates a distributed enforcement problem that compounds over time.

In Cartogra, a multi-tenant service registry platform we're building in public, we made a deliberate decision: the API gateway is the *only* component that issues and validates JWTs. Every other service is behind the perimeter.

**What this means in practice**

When a request arrives at the gateway, `JwtAuthenticationWebFilter` extracts the token — from an httpOnly cookie for browsers, or from `Authorization: Bearer` for API clients. The same filter handles both, trying the cookie first.

If the token is valid, `TenantInjectionGlobalFilter` strips any `X-Tenant-Id` or `X-User-Id` headers from the inbound request and replaces them with values extracted from the validated JWT. Backend services receive headers they can trust unconditionally. A client cannot forge their tenant identity even if they have a valid token.

**Why httpOnly cookies for browsers?**

Tokens stored in `localStorage` are readable by any JavaScript on the page. XSS becomes instant account takeover. `HttpOnly` cookies are inaccessible to scripts. Combined with `SameSite=Lax`, they also resist CSRF on state-mutating endpoints.

API clients can't use cookies easily, so they receive the same token in the response body for use as a Bearer header. One token, two transports — no capability difference.

**The reactive + blocking combination**

The gateway runs on Spring WebFlux (reactive), but user and token lookups use Spring Data JDBC — blocking. This is fine because `spring.threads.virtual.enabled=true` means each blocking call runs on a Java virtual thread. No pinning, no starvation.

**The tradeoff**

The gateway is no longer purely stateless. It holds a PostgreSQL connection for user and refresh token storage, and a Redis connection for OAuth state and rate limiting. This is a conscious choice — the complexity of a separate auth microservice outweighs the benefit for an MVP.

The use-case interfaces (`RegisterUserUseCase`, `LoginUseCase`, etc.) are isolated behind clean boundaries, making a future extraction tractable when the auth surface justifies it.
