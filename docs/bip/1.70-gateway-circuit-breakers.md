## Blog Post (600–1000 words)

**Title:** We Almost Built the Wrong Circuit Breaker

**Hook:** Our own backend conventions told us to wrap every downstream call in a `RestClient` bean and put a circuit breaker around it. Then we went to write the breaker and discovered those `RestClient` classes didn't exist — the gateway had never called services directly at all. Here's what we built instead, and why the "textbook" answer would have been actively wrong for this architecture.

---

**The rule that assumed a class that wasn't there**

Cartogra's backend conventions document (`backend.md`) said: "The Gateway calls downstream services via REST using Spring's `RestClient`... inject a configured `RestClient` bean per downstream service." Reasonable-sounding, and exactly the kind of thing you'd copy from a Spring microservices tutorial.

When we sat down to add circuit breakers for the registry and ingestion services, we went looking for `RegistryClient` and `IngestionClient` to wrap. They didn't exist. Grepping the whole codebase for `RestClient` turned up exactly three usages — Google OAuth, GitHub OAuth, and the Resend email API. Nothing calling our own services.

It turned out the gateway had been built as a Spring Cloud Gateway reverse proxy from day one: routes declared in YAML, no Java client layer at all.

```yaml
routes:
  - id: registry
    uri: ${REGISTRY_URI:http://localhost:8081}
    predicates:
      - Path=/api/v1/registry/**
```

The rule document was describing an architecture that had been quietly abandoned, and nobody had gone back to fix the doc.

**Why this matters for where the breaker goes**

If we'd followed the stale rule literally, we'd have built a `RegistryClient` class just to have something to wrap in a circuit breaker — adding a whole layer of Java code whose only purpose was to host a resilience annotation. That's backwards: the resilience concern should live where the actual call happens, not where a convention document assumed it would.

Since the real call happens in the declarative route, the breaker belongs there too — as a Resilience4j gateway filter attached directly to the route:

```yaml
filters:
  - name: CircuitBreaker
    args:
      name: registry
      fallbackUri: forward:/internal/fallback/registry

resilience4j:
  circuitbreaker:
    instances:
      registry:
        sliding-window-size: 10
        minimum-number-of-calls: 5
        failure-rate-threshold: 50
        wait-duration-in-open-state: 10s
```

No new client class. No new abstraction layer. The breaker instance is named identically to the route id (`registry`), so there's never a translation table to keep in sync between "the route" and "the thing being protected."

**5xx counts as failure too, not just exceptions**

Out of the box, most circuit breaker wiring only trips on network-level exceptions — timeouts, connection refused. A downstream that's technically reachable but returning 500 on every request sails right past that. We explicitly configured both connection exceptions *and* 5xx responses as recorded failures, because "the service is up but broken" is exactly the scenario a circuit breaker exists to catch.

**The health check trap**

The obvious next step is wiring breaker state into `/actuator/health` so it's visible to operators. The less obvious trap: if you let an open breaker flip the aggregate health status to DOWN, Kubernetes will fail readiness and pull the gateway itself out of the load balancer — because one downstream is having a bad day. That's the opposite of what a circuit breaker is for. We expose breaker state as a health *detail*, not as a contributor to the aggregate status.

**The fallback still has to speak the house dialect**

Every Cartogra response follows an envelope: `{"data": T, "traceId": "..."}` on success, `{"error": {...}, "traceId": "..."}` on failure. An open breaker forwards to a small internal controller that throws a `ServiceUnavailableException`, caught by the same `GlobalExceptionHandler` every other domain exception goes through — so a circuit-open response looks exactly like any other API error to a client, just with a `SERVICE_UNAVAILABLE` code and a 503.

**The real lesson**

The interesting bug here wasn't in the code — it was in the documentation describing the code. We fixed `backend.md` alongside the implementation and wrote an ADR (0024) explaining why route-filter breakers are the right call for a declarative-proxy gateway, specifically so the next person who reads the old RestClient-based rule doesn't rebuild a client layer that was never there to begin with.

## LinkedIn Article/Post (300–500 words)

**Title:** The Circuit Breaker Bug That Was Actually a Documentation Bug

When we set out to add circuit breakers to Cartogra's API gateway, our own internal conventions told us exactly how: inject a `RestClient` bean per downstream service, wrap it with Resilience4j. Standard Spring microservices advice.

Except when we went looking for those client classes — `RegistryClient`, `IngestionClient` — they didn't exist. The gateway had been built as a declarative Spring Cloud Gateway reverse proxy from the start: routes defined in YAML, zero Java classes calling our own downstream services. The convention document was describing an architecture that had quietly been abandoned, and nobody had gone back to correct it.

Following the stale rule literally would have meant building a client class with no purpose except to host a circuit breaker annotation — adding a layer of code to serve the documentation instead of the system. We put the breaker where the actual call happens instead: directly on the gateway route, as a Resilience4j filter, named identically to the route it protects.

Two decisions turned out to matter more than the wiring itself.

First: circuit breakers only trip on exceptions by default — timeouts, connection failures. A downstream service that's technically reachable but erroring on every request slips through untouched. We explicitly configured 5xx responses to count as failures too, because "the service responds, but every response is broken" is precisely the failure mode a circuit breaker should catch.

Second: we deliberately kept an open breaker from affecting the gateway's own health status. It would have been easy to wire breaker state straight into `/actuator/health` such that an open breaker drags the whole service to DOWN — but that fails Kubernetes readiness and pulls a perfectly healthy gateway out of the load balancer because one downstream is struggling. Breaker state is visible as a health detail; it doesn't get a vote on the aggregate status.

We corrected the stale convention doc and wrote an ADR explaining the reasoning, specifically so the next engineer who reads "use RestClient per downstream" doesn't go build a client layer that the system never actually had.

The interesting failure here wasn't in the resilience logic — it was in a piece of internal documentation nobody had revisited since the architecture moved on. Worth asking of your own team: which of your written conventions describe a system you don't actually run anymore?
