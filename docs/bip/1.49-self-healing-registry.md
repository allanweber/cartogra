## Blog Post (600–1000 words)

**Title:** The Registry That Reads the Git Repo and Fixes Itself

Every service catalog I've seen has the same long-term failure mode: it starts accurate and drifts.
Engineers update code, forget to update the catalog. Teams change, ownership records go stale. A
new service gets deployed without ever being registered.

Cartogra's answer to catalog drift is not a better form. It's a sync pipeline.

**The drift problem**

Manual registration is optimistic. It assumes engineers will remember to update a catalog entry
when they rename a service, change its owner, or update its OpenAPI spec. In practice, the catalog
is accurate on the day it's populated and degrades from there.

The catalog that's 80% accurate is in some ways worse than no catalog. You can't trust it, so you
don't use it for blast radius analysis or dependency decisions. But it's still there, appearing
authoritative, accumulating stale data.

**The SCM is the source of truth**

Every service that matters lives in a Git repository. The repository has:

- A `service.yaml` (or equivalent) describing the service name, tier, and language
- A `CODEOWNERS` file mapping paths to team ownership
- An OpenAPI spec at a known path (or a `specUrl` in `service.yaml` pointing to one)

If the SCM already has this data, the catalog shouldn't require engineers to enter it again. It
should read it.

**The sync pipeline**

Cartogra's ingestion service runs a sync worker that, given a registered SCM connection, does this:

1. Lists all repositories for the tenant's GitHub organization or Azure DevOps project
2. For each repository, fetches `service.yaml`, `CODEOWNERS`, and the spec URL
3. Upserts the service record in the registry (create if new, update if changed, soft-delete if
   the repo was archived)
4. Resolves team ownership from CODEOWNERS and creates or updates team records
5. Emits a `cartogra.registry.service.synced` Kafka event for downstream consumers

The sync command is idempotent: running it twice produces the same result. If a field hasn't
changed, the `updated_at` timestamp is not bumped. This is enforced at the use-case layer before
the database write (ADR-0014).

**The SPI abstraction**

GitHub and Azure DevOps have completely different APIs, auth models, and repository hierarchies.
Rather than putting provider-specific logic in the use case, Cartogra defines a `ScmProvider`
interface:

```java
public interface ScmProvider {
    String providerType();
    List<ScmRepository> listRepositories(ScmConnectionConfig config);
    Optional<String> getFileContents(ScmConnectionConfig config, String repoPath, String filePath);
    OwnershipMap resolveOwnership(ScmConnectionConfig config, ScmRepository repository);
}
```

`GitHubProvider` and `AzureDevOpsProvider` implement it. The use case doesn't know what GitHub
is — it dispatches by provider type string. Adding GitLab means implementing `ScmProvider` and
annotating with `@Component`. No use-case code changes.

Credentials are passed per-call from the `scm_connections` table (stored as JSONB), not as env
vars. The ingestion service doesn't hold secrets between syncs.

**The "self-healing" property**

Here's the key: the sync is continuous, not one-shot. A webhook receiver in the ingestion service
triggers a targeted sync on every push to a registered repository. A scheduled sync catches
repositories that don't send webhooks.

When an engineer renames a service in `service.yaml`, the next webhook push triggers a sync.
The registry updates. No human action required. The catalog heals itself from the SCM truth.

When a repo is archived, the next sync soft-deletes the service record. When `CODEOWNERS` changes,
team ownership updates. When the spec URL changes, the contract service picks up the new spec on
its next validation run.

The catalog is only as stale as the most recent SCM event. For active repositories, that's seconds.

**What it doesn't solve**

Services that don't live in a registered SCM connection still require manual registration. The sync
pipeline extends trust to the boundary of the tenant's registered SCM accounts — not beyond it.
Similarly, services with no `service.yaml` won't be auto-discovered. The file is the contract
between the service team and the catalog.

The long-term answer for the first problem is a CI/CD integration that automatically registers a
service on its first successful deploy. That's a later phase. The sync pipeline is the foundation
it builds on.

## LinkedIn Post (300–500 words)

**Title:** The service catalog that reads your Git repo — solving catalog drift with continuous sync

Service catalogs have a predictable lifecycle: populated accurately on day one, accurate enough
to trust for a few weeks, and then gradually wrong in ways that are hard to notice until they
matter.

The cause is structural. Manual registration depends on engineers remembering to update a catalog
when they update code. Most of the time, they don't. The catalog drifts.

**The source of truth already exists**

Every service that matters lives in a Git repository. The repository already has the data the
catalog needs: a service manifest with the name, tier, and tech stack; a CODEOWNERS file
capturing team responsibility; an OpenAPI spec describing the API contract. If that data is in
Git, requiring engineers to also enter it into a catalog is asking for duplication and
inevitable divergence.

**Cartogra's sync pipeline**

The ingestion service connects to a tenant's GitHub organization or Azure DevOps project and
runs a continuous sync. It reads `service.yaml`, resolves CODEOWNERS to team records, and
upserts service entries in the registry. Webhook receivers trigger targeted syncs on every push,
typically completing within seconds. A scheduled full sync catches repositories that don't
surface webhooks.

A `ScmProvider` SPI abstracts the differences between GitHub and Azure DevOps. The core sync
use case dispatches by provider type string — it doesn't contain any GitHub-specific logic.
Adding GitLab in a future phase means implementing one interface, not modifying the sync
pipeline.

**The self-healing property**

When an engineer renames a service in `service.yaml`, the next push triggers a sync and the
registry updates without human intervention. When a repository is archived, the service record
is soft-deleted. When CODEOWNERS changes, team ownership updates. The catalog converges to Git
truth automatically.

For platform and SRE teams, this changes the question from "is the catalog accurate enough to
trust?" to "when was the last sync?" — a much more tractable question to answer.

**What remains manual**

Services outside registered SCM connections still require explicit registration. The sync
pipeline extends trust to the boundary of the tenant's connected accounts. Services with no
`service.yaml` are not auto-discovered. The file is the contract between the service team and
the catalog infrastructure.

For teams managing large service estates: what's the biggest source of catalog drift you're
dealing with today, and is it a data entry problem or a process problem?
