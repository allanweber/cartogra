## Blog Post (~1000 words)

### A span is not an edge

A dependency graph wants `A → B`. OpenTelemetry gives you spans: a CLIENT span in A, maybe a SERVER span in B, linked by a parent span id, with whatever attributes the instrumentation library felt like setting. Turning one into the other is mostly a list of decisions about what to believe. These are ours (ADR-0029).

### The pipeline

The OTel Collector exports raw OTLP/JSON to a Kafka topic, `cartogra.observability.spans`. Topology's `OtelSpanWorker` consumes it and parses only the fields it needs, ignoring the rest. Edges are upserted on the existing edge-identity index (`tenant, source, target, type, protocol`), so replaying a record never creates a duplicate edge.

This topic breaks our own rule that every Kafka message is wrapped in the platform envelope. The collector can't wrap anything, so the exception is written down instead of being worked around.

### Decision 1: whose span is it?

Topology is multi-tenant, and spans have no idea what a tenant is. Spans carry a resource attribute, `cartogra.tenant.id`. A missing or malformed tenant, or a tenant with no services, sends the record to a DLQ with a reason counter (`cartogra.spans.quarantined{reason}`). We don't guess.

The honest part: that attribute is unauthenticated today. Anyone who can reach the collector can claim a tenant. That's acceptable for a dev stack and nothing else, and trusted intake through the gateway with API keys is on the roadmap (5.9).

### Decision 2: who is the target?

A CLIENT span names its target badly. In order:

1. `peer.service`, if the instrumentation set it.
2. The host of `server.address`, port stripped.

Both are matched against the catalog by lowercased name. An IP address matches nothing, which is the common case.

### Decision 3: when the client can't say, ask the server

If the CLIENT span's target doesn't resolve, we wait for the SERVER span whose `parent_span_id` is the client's `span_id`. That span knows exactly which service it is.

The two halves can arrive in any order, in different Kafka records, on different instances. So the waiting half is persisted in `pending_span_links` with a 5-minute TTL instead of kept in memory. The lookup-or-park step runs under a per-tenant Postgres advisory lock. Without it, two instances could each park their half and never see the other.

An in-memory join was simpler and we rejected it: it loses halves on restart and breaks the moment there are two instances.

### Decision 4: Kafka doesn't have parents

A producer and its consumers don't share a parent span, and often not even a trace. So messaging edges join on the topic name: every PRODUCER of `payments.completed` gets a `kafka` edge to every CONSUMER of it. Each side is one row per (tenant, topic, kind, service), refreshed by traffic and kept for 24 hours. It isn't deleted on match, because the next consumer might show up tomorrow.

### Decision 5: databases only count if you told us about them

A CLIENT span with `db.system` becomes a `db` edge only if the database matches a catalog service (`peer.service`, then `db.namespace`, then the host). Anything else is dropped.

We deliberately don't list unmatched databases as unresolved. Names like `postgres` and `main` would bury the list that's actually useful.

### What we throw away, on purpose

- **Spans with no protocol we understand.** HTTP and gRPC are detected from semantic-convention attributes. Anything else is skipped and counted.
- **IPs and bare hosts as names.** They never go into the unresolved list.
- **Cartogra's own spans.** The collector filters them out, otherwise the worker would observe itself consuming spans.
- **Unbounded unknowns.** Unmatched `peer.service` names go into an "unresolved services" list (with a "create service" shortcut in the UI), capped at 1000 per tenant, because span data is untrusted input.
- **Write amplification.** `last_seen_at` is refreshed only when it's more than a minute stale. A chatty service doesn't rewrite its edge row on every request.

### What we haven't solved

Sampling: if the call isn't sampled, it isn't observed. Uninstrumented proxies: an ingress that forwards `traceparent` but emits no span makes the server look like it was called by nobody. And the advisory lock serialises the unmatched path per tenant, which is fine at our scale and something we'll watch.

### Testing it without a collector

Every rule above has a JSON fixture under `services/topology/src/test/resources/otel/`. Fixtures are published straight to Kafka in Testcontainers ITs, so the whole path runs in CI with no collector. The Acme seed then checks the same rules end to end against real spans.
