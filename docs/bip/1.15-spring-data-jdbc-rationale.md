# BIP 1.15 — Spring Data JDBC: Why Explicit SQL Beats ORM Magic

> ADR: [ADR-0009](../adr/ADR-0009-spring-data-jdbc.md)

---

## Blog Post

**Title:** Why I chose Spring Data JDBC over Hibernate — and what I gave up

Every Spring tutorial starts with JPA. Every Spring Boot quickstart wires up Hibernate. For years I defaulted to it without questioning the choice.

Then I had a `LazyInitializationException` in production on a Friday evening, traced it to a DTO projection missing an `@Transactional` annotation three layers up the call stack, and spent two hours debugging Hibernate's session lifecycle instead of my business logic.

When I started Cartogra I made a different call: Spring Data JDBC. Here's what that means in practice.

**What Spring Data JDBC is**

Spring Data JDBC is a persistence layer that sits on top of `NamedParameterJdbcTemplate`. It gives you repositories, `@Query` for custom SQL, and `RowMapper`-based result mapping. It has no session, no L1 cache, no lazy loading, and no proxy objects.

When you call `repository.findById()`, it runs one SQL statement. Always. The result is a fully populated Java record. There is no "unitialized proxy" to stumble over later.

**The multi-tenant argument**

Cartogra has a `tenant_id` on every domain table. Every query filters by it. Hibernate can do this, but it requires either a multi-tenancy interceptor (complex to configure, invisible in code review) or explicit WHERE clauses in every `@Query`. Spring Data JDBC just writes explicit SQL — the `tenant_id` filter is visible in every query, reviewable in every PR, and obvious to anyone reading the code a year from now.

```java
// What you see is what you get
private static final String FIND_BY_ID = """
    SELECT * FROM services
    WHERE id = :id AND tenant_id = :tenantId AND deleted_at IS NULL
    """;
```

**JSONB and recursive CTEs**

Cartogra stores tech stack detection results and service metadata as JSONB. Flyway migrations add GIN indexes. Queries use `@>` containment operators and `to_tsvector` for full-text search.

JPA handles these with `@Formula` or `@NativeQuery`, which bypasses the type system and loses refactoring safety. Spring Data JDBC doesn't pretend — it's SQL all the way down. The JSONB operator in a `NamedParameterJdbcTemplate` query is exactly what reaches the database.

**What I gave up**

- **Dirty tracking**: I must call `save()` explicitly. For a REST API that receives a full update body, this is one extra method call. For a domain with many partial updates, it could be more code.
- **Optimistic locking**: No `@Version`. If I need it, I add a `WHERE updated_at = :prev` check in the update SQL.
- **Auto-schema generation**: Flyway owns DDL. This is already a project rule, so it's not a cost — it's a constraint I welcome.

**The bottom line**

SQL is a public API between your application and your database. When that API is generated invisibly at runtime, your pull requests don't show the queries that matter. Spring Data JDBC makes the persistence layer an explicit, reviewable artifact. For a multi-tenant, audit-heavy domain, that's the right trade.

## LinkedIn Article

**Title:** Why I chose Spring Data JDBC for a multi-tenant SaaS — the honest tradeoffs

JPA and Hibernate are the default choice for Spring persistence. They're well-documented, widely understood, and handle a large class of persistence problems cleanly.

They also abstract away the SQL that actually runs against your database — and in a multi-tenant, audit-heavy system, that abstraction becomes a liability.

**What changed my mind**

A `LazyInitializationException` traced to a missing `@Transactional` annotation three layers up the call stack. Two hours debugging Hibernate's session lifecycle instead of the business logic that was failing. The fix was one annotation — but finding it required understanding the ORM's internal state management.

That's a tax I pay every time the abstraction leaks. For simple CRUD on a single-tenant system, it's manageable. For Cartogra — where every query filters by `tenant_id`, every mutation writes an audit snapshot, and the data model includes JSONB columns and recursive graph queries — it became noise I couldn't afford.

**Spring Data JDBC: what it gives you**

A thin layer over `NamedParameterJdbcTemplate` with repository interfaces and `@Query` support. No session, no L1 cache, no proxy objects. `findById()` runs one SQL statement. The SQL is in your code, visible in pull requests, and executed exactly as written.

For a team maintaining a multi-tenant codebase where the `tenant_id` filter is a security boundary — not just a convenience — the ability to review every query in code review is worth more than dirty tracking or lazy loading.

**The honest tradeoffs**

- **No dirty tracking**: `save()` must be called explicitly after any mutation.
- **No `@Version` optimistic locking**: implemented with a `WHERE updated_at = :prev` guard in the SQL if needed.
- **No schema generation**: Flyway owns DDL. This was already a project constraint, so it's not an added cost.

These are real trade-offs. The test is whether the benefit — visible, reviewable, explicit SQL — outweighs them in your domain. For Cartogra, it does.

What persistence patterns have you standardized on for multi-tenant systems? I'd be curious what's worked.
