## Blog Post (600–1000 words)

**Title:** Why Auth Lives in the Gateway — and Nowhere Else

The most common mistake I see in Spring microservice tutorials: adding `spring-boot-starter-security`
to every service and having each one validate JWTs independently. It's the path of least resistance
and a long-term maintenance problem.

Cartogra made the opposite choice. Auth lives in the gateway. The five other backend services don't
touch a token.

Here's the reasoning, the implementation, and the OAuth integration strategy.

**The per-service auth trap**

When every service validates tokens independently, the operational surface area compounds quietly:

- JWT secret rotation requires a coordinated redeploy of every service simultaneously.
- Rate limiting before credential validation requires every service to implement it — or you do it
  inconsistently.
- A new OAuth provider means updating auth logic in five places.
- One service running a stale JWT library version creates a silent security divergence.

These costs are low in the first month. They accumulate over quarters.

**The gateway as the perimeter**

In Cartogra, the `gateway` service (port 8080) is the only component that issues and validates
JWTs. The Spring Cloud Gateway routing layer and Spring Security 7 ReactiveSecurityContextHolder sit
in the same process. Rate limiting, auth, and routing share one Redis connection pool. Tenant context
injection happens once, immediately after token validation, and is propagated to downstream services
via injected headers — not re-derived.

Downstream services (registry, topology, contract) receive `X-Tenant-Id` and `X-User-Id` headers
injected by the gateway's `TenantInjectionGlobalFilter`. They never see a token. They cannot forge
one. In production, Kubernetes NetworkPolicy adds a second enforcement layer.

This is documented in ADR-0010: the gateway is the sole token issuer for MVP scope. When auth
complexity grows past what a single gateway can manage — SCIM provisioning, device flow, federated
identity — the use-case boundaries (`RegisterUserUseCase`, `LoginUseCase`) are clean enough to
extract to a dedicated auth service without touching the downstream services at all.

**Dual-mode: cookie for browsers, Bearer for API clients**

Browsers and API clients have fundamentally different constraints:

- A browser can't easily attach an `Authorization: Bearer` header to a form submit or a redirect.
  But it can automatically send an `httpOnly; Secure; SameSite=Lax` cookie — one that JavaScript
  cannot read (XSS cannot steal it).
- A CI pipeline or CLI tool can't handle cookies. It needs a raw token for the `Authorization`
  header.

The solution is to issue the same JWT and deliver it two ways on login. The `AuthController` sets
an `httpOnly` cookie AND returns the token in the response body:

```java
response.addCookie(ResponseCookie.from("jwt", tokens.accessToken())
    .httpOnly(true).secure(true).sameSite("Lax").path("/")
    .maxAge(tokens.expiresIn()).build());
// Body also has access_token for API clients
return ResponseEntity.ok(new ApiResponse<>(tokens, traceId));
```

The filter tries cookie extraction first, then `Authorization: Bearer`. Cookie takes precedence —
it matches browser behavior without penalising API clients.

A third mode exists for CI pipelines: `X-Cartogra-Api-Key`, a tenant-scoped API key that bypasses
JWT entirely. Same security boundary, different credential type. This is ADR-0011.

**OAuth integration strategy**

OAuth providers (Google, GitHub, GitLab) are supported via Spring Security 7's reactive OAuth2 client.
The gateway handles the OIDC authorization code flow end-to-end: redirect to provider, receive the
code, exchange for an ID token, validate claims, and issue a Cartogra JWT.

The key decision: we issue a Cartogra JWT after OAuth, rather than forwarding the provider token.
Provider tokens have variable expiry, variable claim shapes, and no `tid` (tenant ID) claim.
Cartogra needs a consistent JWT with `{ sub, tid, roles[], exp }` regardless of how the user
authenticated. The OAuth provider becomes an identity source, not a token issuer.

The OAuth state is stored in Redis with a short TTL — one round trip, no persistent DB write for
the handshake. The mapping from provider identity to Cartogra user is in PostgreSQL.

**The enforcement gap that gets missed**

One pattern that looks like it works but doesn't: stripping `X-Tenant-Id` from inbound client
requests at the gateway but not re-injecting it from the token. If you forget the re-injection,
services that trust the header get no tenant context and either throw or return data for the wrong
tenant.

The Cartogra `TenantInjectionGlobalFilter` does both in one step: strip the inbound header, then
add the header derived from the validated JWT `tid` claim. One filter, one place, enforced on every
proxied request.

## LinkedIn Post (300–500 words)

**Title:** Auth in the gateway — the centralisation decision that simplifies everything downstream

When we started building Cartogra, we faced an early architectural fork: should each microservice
validate JWTs independently, or should auth live in a single place?

We chose a single place — the API gateway.

**The hidden cost of per-service auth**

Distributing JWT validation across five services seems straightforward until you need to rotate a
secret. Suddenly you're coordinating a simultaneous redeploy across every service, hoping none of
them hit the key-validity gap. Rate limiting before credential validation requires either
duplicating the logic or accepting inconsistent enforcement. A new OAuth provider means updating
auth code in five places.

These aren't theoretical risks. They're operational costs that compound quietly over months.

**The gateway as the auth perimeter**

In Cartogra, the `gateway` service (port 8080) is the only component that issues or validates JWTs.
Spring Security 7's reactive filter chain handles the OIDC authorization code flow, local credential
validation, rate limiting, and tenant context injection in one process. Downstream services receive
`X-Tenant-Id` and `X-User-Id` as injected headers — they never see a raw token.

This makes secret rotation a gateway-only operation. Adding a new OAuth provider means updating
one service. Rate limiting is enforced once, before any credential check begins.

**Three transport modes, one security model**

Browser clients get an `httpOnly; Secure; SameSite=Lax` cookie — the JWT is invisible to
JavaScript, so XSS cannot exfiltrate it. API clients use a standard `Authorization: Bearer` header.
CI pipelines use a scoped `X-Cartogra-Api-Key`. Same security boundary, three delivery mechanisms,
one authentication filter that tries them in order.

**The planned extraction point**

This consolidation is explicitly scoped to MVP. When auth complexity grows — SCIM provisioning,
device flow, federated identity across multiple gateways — the use-case interfaces
(`RegisterUserUseCase`, `LoginUseCase`) are already isolated behind clean hexagonal boundaries.
Extraction to a dedicated auth service won't touch any downstream service. The reversal conditions
are written into ADR-0010.

For teams building multi-service APIs: how are you handling the tension between centralised auth
simplicity and the operational risk of the auth gateway becoming a single point of failure?
