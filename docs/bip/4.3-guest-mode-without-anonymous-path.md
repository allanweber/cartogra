# BIP 4.3 — Guest Mode Without an Anonymous Auth Path

**Format:** short post (thread + LinkedIn). Blog, Instagram and video N/A: ADR-0019 is the long form.
**Publish after:** Phase 4 gate closed

---

## Twitter/X Thread (6 tweets)

1/ A public demo needs a "no login" button. The usual implementation is a set of routes that skip auth. One wrong route, and a stranger can write. We built guest mode with zero unauthenticated routes. 🧵

2/ `/demo` calls the gateway, which mints a normal JWT: `roles=["GUEST"]`, a random UUID `sub`, the demo tenant, 60 minutes, httpOnly cookie. After that, a guest goes through the same filters as every user.

3/ Primary guard: the gateway rejects every guest request that is not GET/HEAD/OPTIONS with 403, before it proxies. It fails closed, also for endpoints that do not exist yet. `@PreAuthorize` on each write is the second layer.

4/ The IT does not sample. It lists every write route in every service and asserts 403 for a guest token. A new route that nobody added to the list fails the build.

5/ Blocking writes is not enough. Reads are redacted in the backend: no emails, no user ids, no OIDC config. The audit feed is an allowlist of fields declared guest-safe.

6/ And two keys: the config sets the guest tenant id, but the tenant row must also have `public_sandbox`. A wrong id opens nothing. [link] #BuildInPublic

## LinkedIn Post (~320 words)

Every public demo has a "try it without an account" button. The common implementation adds routes that skip authentication and inject a fake identity. That design has a failure mode: one route in the wrong list, and an anonymous visitor can change data.

For Cartogra's public instance, we built guest mode with no anonymous path at all (ADR-0019).

- **A guest gets a real token.** `/demo` asks the gateway to mint a 60-minute JWT with the role `GUEST`, bound to the demo tenant. Tenant injection, rate limits and RBAC work as they do for every user. Nothing in the backend has a special case for "no user".
- **The gateway blocks writes by HTTP method.** A guest request that is not GET, HEAD or OPTIONS gets 403 before it reaches a service. This guard fails closed, also for endpoints that we have not written yet. `@PreAuthorize` on each write is defence in depth.
- **The test enumerates, it does not sample.** An integration test lists every write route and asserts 403 for a guest.

Two lessons came after the first version:

1. **Read-only is not the same as safe.** A guest could read user emails and OIDC settings. Now the backend redacts personal data for a guest. The audit feed shows only the fields that we declared guest-safe. We do this in the API, not in the UI, because anything that the browser receives is readable.
2. **One config value must not make a tenant public.** The guest tenant needs a database flag too, and only the bootstrap of a new tenant can set it.

The result: a stranger can click one link, explore a real tenant and change nothing.

How do you give strangers access to your product without a second auth system?
