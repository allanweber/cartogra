## Blog Post (~900 words)

### The question every catalog gets

"Who changed the owner of `ledger-service`, and when?"

In Cartogra, that change can come from five places. A user edits the service in registry. The gateway changes an OIDC setting. Topology declares an edge or resolves a drift. Ingestion discovers a service in Kubernetes. Contract stores a new API version. Each service has its own schema. The Timeline must show all of them, in one list, for one tenant.

### The naive fix: every service writes one shared table

The obvious answer is one `audit_events` table and an `INSERT` in every service. It works on day one. Then it costs you three things:

- **Every service gets the credentials for one schema it does not own.** The schema boundary that you drew on purpose is gone.
- **A migration on that table is a deploy of five services.** Nobody owns the shape, so nobody can change it.
- **Erasure has no single owner.** GDPR erasure must anonymise audit rows. If five services write them, five services must agree on how.

The other naive fix is one audit table per service. Then the Timeline must query five databases and merge the results. Pagination across five sources is a bad week.

### The real fix: one owner, one port, two adapters

We decided this in ADR-0017.

**Registry owns `audit_events`.** It is the only writer of record. RLS on the table enforces the tenant boundary, the same as every other table in registry.

**`shared:common` defines a port, not a writer:**

```java
public interface AuditEventPort {
    void record(AuditEvent event);
}
```

`shared:common` is plain Java with no Spring, so it cannot hold a JDBC writer. It does not need one. A domain service calls `record(...)` and does not know where the row goes.

**Each service picks an adapter in one `@Configuration` class:**

| Service | Adapter | What happens |
|---|---|---|
| registry, gateway | `JdbcAuditEventAdapter` | `INSERT` in the same transaction as the change. The row commits or rolls back with it. |
| topology, ingestion, contract | `KafkaAuditEventAdapter` | After commit, publish one envelope to `cartogra.platform.audit.recorded`. |

Registry consumes the topic and writes the row with `ON CONFLICT (event_id) DO NOTHING`. The event id is deterministic, so a Kafka redelivery writes nothing new. One topic for all producers is enough: audit is one kind of event, not one kind per entity.

### Three details that matter more than the diagram

**1. Publish after commit, never before.** The Kafka adapter registers a `TransactionSynchronization` and sends in `afterCommit`. If the edge change rolls back, nobody sees an audit row for a change that did not happen.

**2. The audit never fails the change.** The send runs on a virtual thread. If the broker is slow or down, the mutation still returns 200. This is a trade-off, and we wrote it down: if the send fails, the adapter logs a warning and that row is lost. For a catalog Timeline, we accept that risk. For `dependency.changed`, which another service acts on, we did not accept it: that topic goes through a transactional outbox (story 5.4).

**3. The payload is an allowlist.** Each entity kind declares its payload fields in `AuditKind`. A field that nobody declared never enters the payload, so a secret cannot leak into the audit by accident. The same list controls what a guest can see (ADR-0019 §8).

### What we do not audit

We audit state changes only. We do not audit logins, token refreshes, guest token mints or the `last_seen` update from each OTel span. A span stream would put thousands of rows per minute into the Timeline, and nobody can read thousands of rows. An audit trail that records everything tells you nothing.

### What it looks like

The Timeline and the dashboard activity feed read `GET /api/v1/registry/audit-events`. They show each change with the actor (a user or `system`) and the fields before → after. Every role can read it, guest included, because the audit is a product surface, not an admin tool.

### What I would change

The Kafka path is "at least once after the broker accepts it", not "at least once". The outbox from 5.4 now exists in `shared/web`. If an audit gap ever matters to a customer, the fix is one adapter change in three `AuditConfig` classes. The domain code does not change. That is the reason for the port.

## LinkedIn Post (~350 words)

In a system with several services, the audit log is the first thing that makes you decide who owns what.

In Cartogra, changes come from five services: registry, gateway, topology, ingestion and contract. The product needs one Timeline per tenant. The fast answer is one shared table that every service writes. We decided against it. A shared table gives every service access to a schema it does not own, and it makes every migration and every GDPR erasure a cross-team task.

Our design has three parts:

- **One owner.** Registry owns `audit_events`. It is the only writer of record.
- **One port.** A plain-Java `AuditEventPort` in the shared module. Domain code calls `record(...)` and does not know the transport.
- **Two adapters.** Services on the registry schema insert in the same transaction. The other services publish to one Kafka topic after commit, and registry consumes it idempotently.

The decision that took the longest was a trade-off, not a technology. The Kafka publish never blocks or fails the user's change. If the broker is down, that audit row is lost. For a Timeline, that is acceptable. For events that another service acts on, it is not, and those go through a transactional outbox. Because the port isolates the transport, we can move audit to the outbox later with no change to domain code.

We also audit less than you expect: state changes only. No logins, no token refreshes, no update per trace span. An audit trail that records everything is a log that nobody reads.
