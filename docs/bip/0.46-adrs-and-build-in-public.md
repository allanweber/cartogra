## Blog Post (~600 words)

### The Decision You Didn't Document Will Haunt You

Code is easy to read. You can grep for a function, trace a call stack, read a test. The decision that produced that code — the constraint that ruled out three alternatives, the incident that forced the approach, the trade-off that still holds — that is invisible unless someone wrote it down at the time.

Six months later, a new engineer asks: "Why are we using PostgreSQL for graph queries instead of Neo4j?" The answer is not in the code. It is either in the memory of whoever made the call (who may have left the company), in a Slack thread that aged out of the free tier, or nowhere.

Architecture Decision Records fix this.

**What an ADR is**

An ADR is a short document that captures a single architectural decision: the context that made it necessary, the options considered, the decision made, and the consequences that follow from it.

The format is deliberately minimal:

```
Title: ADR-0001 — Use PostgreSQL over a graph database for graph queries
Status: Accepted
Context: We need to traverse multi-hop dependency graphs across services...
Decision: Use PostgreSQL with recursive CTEs...
Consequences: Graph queries require careful index design...
```

No elaborate diagrams. No lengthy justification. One decision, one record.

The value is not in the format — it is in the habit. ADRs turn decisions from verbal agreements that evaporate into documented choices that survive team turnover, reorgs, and memory loss.

**ADR-0001: Why PostgreSQL over a graph DB**

Cartogra needs to traverse multi-hop dependency graphs — blast radius analysis, cycle detection, ancestor traversal. The natural tool is a graph database like Neo4j.

ADR-0001 explains why we chose PostgreSQL with recursive CTEs instead.

The core reasons: the system is already multi-tenant with strong PostgreSQL constraints (row-level security, ACID transactions, Flyway migrations). Adding a second database engine adds ops complexity, failure modes, and an additional learning curve. PostgreSQL's recursive CTE support is mature and handles the traversal depths we need (max 25 hops). The query patterns are read-heavy with writes on dependency creation — no streaming graph algorithms that would justify a graph DB.

The constraint that mattered: at MVP scale, operational simplicity beats algorithmic elegance. One database, one backup strategy, one set of connection pool tuning parameters.

This decision will be revisited when graph query latency becomes measurable under real tenant load. That revision will be its own ADR.

**ADR-0003: gRPC for internal synchronous calls**

The other ADR worth highlighting: all direct service-to-service calls use gRPC, not REST.

The driving constraint was type safety and contract enforcement. JSON REST calls between services are hard to validate — the client and server agree on a shape only by convention. Proto files in a shared `contracts` module enforce the shape at compile time. Any breaking change to an internal API fails the build before it reaches review.

The secondary benefit is observability: OpenTelemetry auto-instruments gRPC channels, so every internal call appears in traces with latency breakdowns, without any manual instrumentation.

**Building in public means documenting decisions**

The ADR process is itself a BIP artifact. Writing ADRs while building forces clarity: if you cannot explain the decision in four sections, you probably have not made the decision yet — you have made a guess.

Publishing them publicly turns a private engineering practice into a visible artefact of how and why the system is being built the way it is.

All Cartogra ADRs: [docs/adr/](https://github.com/allancassiano/cartogra/tree/main/docs/adr)

## LinkedIn (~300 words)

**The engineering practice that makes build-in-public meaningful**

Most build-in-public content shows the code. The harder part to show — and the more valuable — is the decisions behind the code.

Architecture Decision Records (ADRs) are a structured way to capture those decisions. Each record covers one choice: what context made the decision necessary, what alternatives were considered, what was chosen, and what consequences follow. The format is intentionally minimal — short enough to write in 20 minutes, long enough to survive team turnover and org changes.

The practice is valuable even in private. Made public, it becomes something more: a visible record of how and why a system is being built the way it is. That is what build-in-public engineering actually means — not just code on GitHub, but reasoning that external engineers can learn from.

For Cartogra, ADR-0001 explains why we use PostgreSQL with recursive CTEs for graph queries rather than a dedicated graph database. The short version: the system is already fully committed to PostgreSQL for multi-tenancy guarantees, adding a second database engine adds significant ops overhead, and recursive CTEs handle our traversal depths at MVP scale. This will be revisited when graph query latency becomes measurable under real tenant load — and that revisitation will produce its own ADR.

ADR-0003 explains why all direct service-to-service calls use gRPC rather than REST. The core driver is compile-time type safety: proto files in a shared contracts module enforce the API shape at build time, so breaking changes fail the build before review, not in production.

If you are building a platform or service-oriented system, ADRs are the lowest-effort highest-return documentation practice I know of. You are making these decisions anyway. Writing them down takes 20 minutes and pays off for years.
