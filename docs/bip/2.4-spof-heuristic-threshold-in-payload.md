## Twitter/X Thread (4 tweets)

1/ "Single point of failure" in a dependency tool is a *heuristic*. Ours: fan-in ≥ 5 distinct dependents. That number is arbitrary. So the API says so, in every response. 🧵

2/ `GET /spofs` →

```json
{
  "threshold": 5,
  "rationale": "Services with 5 or more direct dependents are flagged as single points of failure; severity escalates to CRITICAL for CRITICAL-tier or unowned (orphan) services.",
  "items": [...]
}
```

The threshold and why ride with the data.

3/ Why: a consumer (UI, CI gate, a script) seeing 3 SPOFs should know whether that's "3 at ≥5" or "3 at ≥2" without opening docs that drift. Per-tenant override exists in the schema; default 5.

4/ What it doesn't know: whether a replica exists, whether the call is on the hot path, traffic volume. Fan-in is structure only. Calling it "heuristic" in the payload is cheaper than explaining a false positive later. [link] #BuildInPublic

## LinkedIn Post (~250 words)

Our tool flags "single points of failure." I don't want anyone to read that as a fact.

It's a heuristic: a service with at least 5 distinct dependents is flagged. Severity goes to CRITICAL if the service is tagged CRITICAL tier or has no owning team. That's it. It doesn't know whether the service has replicas, whether the dependents call it on a hot path, or how much traffic crosses the edge. Fan-in measures structure, not risk.

So instead of burying that in documentation, the API returns it with every response: the threshold in use, and a plain-language rationale, next to the items. Anything that consumes the endpoint — the UI, a script, a future CI check — can show *why* something was flagged without a trip to the docs, and the docs can't drift from the behavior because there's one source for both.

The threshold is also tenant-configurable in the schema, with a default of 5. (Honest status: read-only today; the write endpoint doesn't exist yet.)

A scoring system that hides its cutoff invites people to treat it as ground truth, and then it gets argued with instead of used.

Do the risk scores in your tooling say how they're computed?
