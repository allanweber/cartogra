# BIP 1.37 — GitHub vs Azure DevOps Provider Comparison

## Blog Post (600–1000 words)

### GitHub vs Azure DevOps: Building Both SCM Adapters and What We Learned

With Cartogra's `ScmProvider` SPI defined, we built both adapters. Here's what we found when we went deep on both APIs — including some surprises.

**The Common Shape**

Both providers need to satisfy three operations: list repositories, fetch file contents, resolve code ownership. The SPI forced us to map each provider's concepts to a common model before writing a single line of adapter code.

For repositories, the mapping is straightforward:

| Concept | GitHub | Azure DevOps |
|---------|--------|-------------|
| Org unit | `org` | `organization` + `project` |
| Repo ID | integer | UUID |
| Archived flag | `archived: boolean` | not supported (we default `false`) |
| Default branch | `default_branch` | `defaultBranch` (with `refs/heads/` prefix) |

The AzDO `refs/heads/` prefix is a small gotcha — you need to strip it to get `main` from `refs/heads/main`. We handle this in the mapper.

**Auth: PAT is Universal, but the Encoding Differs**

GitHub PATs go in the `Authorization: Bearer <token>` header.

Azure DevOps PATs go in a Basic auth header where the username is empty and the password is the PAT:

```java
Base64.encode(":" + pat)  // note the colon prefix
```

This is AzDO's quirk — the empty username is required. `AzureDevOpsAuthHelper` encapsulates this so the provider class never touches raw auth encoding.

We deliberately did not implement Azure DevOps service-principal (client credentials) auth in this iteration — it requires an OAuth token exchange flow and a separate callback URL. We document this as a follow-up task. The `config` map accepts `pat` for now; a future `clientId`/`clientSecret` path can be added to `AzureDevOpsAuthHelper` without touching the SPI.

**Ownership: CODEOWNERS vs Team Policies**

Both providers support a `CODEOWNERS` file. GitHub puts it at the repo root, `.github/CODEOWNERS`, or `docs/CODEOWNERS`. Azure DevOps uses the same convention (or `.azuredevops/CODEOWNERS`). The file format is identical — a path pattern followed by owner references.

The difference is in owner reference syntax:
- GitHub: `@org/team-name`
- Azure DevOps: `[Team Name]` or `DOMAIN\username`

For the `OwnershipMap`, we collect GitHub-style `@org/team-name` references into `ownerTeams`, and AzDO-style `[Team Name]` references similarly. The upstream consumer (topology service, eventually) will handle the display difference.

**API Rate Limiting**

GitHub enforces a 5,000 request/hour limit on PAT-authenticated REST calls. For a large org with hundreds of repos, each `resolveOwnership` call fetches the `CODEOWNERS` file — that's one request per repo. For an org with 500 repos, a full sync uses ~500 requests. Staying well under the limit.

Azure DevOps doesn't publish a specific rate limit for REST API calls, but throttles under sustained load. Our provider makes sequential requests per project. For large orgs with many projects, we may need to add pagination or parallelism — flagged as a future improvement.

**WireMock Tests: What Worked and What Didn't**

The `apiBaseUrl` override in `ScmConnectionConfig` worked perfectly for unit-level WireMock tests. The provider creates its `RestClient` using that base URL, so WireMock intercepts all calls without any env var mocking.

One issue we hit: GitHub's content endpoint returns base64-encoded content with embedded newlines (`\n` every 60 chars). The decoder needs to strip both newlines and spaces before decoding. Our first iteration missed this and failed to decode multi-line CODEOWNERS files.

```java
String cleaned = encoded.replace("\n", "").replace(" ", "");
return new String(Base64.getDecoder().decode(cleaned));
```

**What's Next**

The sync worker (Kafka consumer) that drives these providers is live. The next step is surface area in the registry service: a `POST /connections` endpoint that stores connection config, and a scheduler that periodically publishes sync commands for each active connection.

If you're building a similar multi-provider integration — define the SPI before the first implementation. It forces you to find the common model early, when changing it is cheap.

## LinkedIn Post (300–500 words)

**GitHub vs Azure DevOps: what building both adapters taught us about API design**

We shipped both SCM provider adapters for Cartogra this week — GitHub and Azure DevOps. Here are the three things that surprised us about the APIs, and one engineering practice that saved us each time.

**1. Auth encoding is subtly different**

GitHub PATs go in `Authorization: Bearer <token>`. Clean and modern.

Azure DevOps PATs go in Basic auth — but the username is **empty**. You encode `":" + pat` (note the colon). Forget the colon and you get a 401 with no helpful message. We caught this on the first WireMock test.

**2. Azure DevOps has a project hierarchy that GitHub doesn't**

GitHub is flat: organization → repository. Azure DevOps is: organization → project → repository. Listing all repositories requires first listing all projects, then querying each project. For orgs with many projects, this is more API calls than the equivalent GitHub query. We handle this sequentially for now and flag parallelism as a future improvement.

**3. GitHub base64-encodes file contents — with embedded newlines**

GitHub's content API returns file contents as base64, but inserts a `\n` every 60 characters. Standard `Base64.decode()` rejects this without stripping newlines first. The `CODEOWNERS` file is usually multi-line, so this hits on almost every ownership resolution. One failing WireMock test, one strip-before-decode fix.

**The practice that saved us each time: WireMock-first**

Before writing the adapter, we write the WireMock stub for the expected response — including the exact encoding quirks (base64 with newlines, refs/heads/ prefix, empty Basic auth username). This forces us to read the actual API documentation rather than assuming the happy path. Every quirk above showed up as a failing test before it could show up in production.

Both adapters are live. Both have passing WireMock tests. The next step is the registry-side `POST /connections` endpoint and a sync scheduler.
