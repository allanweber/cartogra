## Blog Post

**Title:** Why I didn't add Neo4j to my service catalog — and what I use instead

When I started building Cartogra, a living service registry with dependency intelligence, the data model seemed to scream "graph database." Services are nodes. Dependencies are edges. Blast radius is a traversal. Cycle detection is a classic graph algorithm. Neo4j, Amazon Neptune, and TigerGraph would all handle these patterns natively.

I chose PostgreSQL and I don't regret it. Here's why.

**The scope of the problem matters**

At startup scale, the graph is small. Cartogra's target customer has tens to hundreds of services — not millions of nodes and billions of edges. PostgreSQL's recursive CTEs (`WITH RECURSIVE`) handle these traversals in tens of milliseconds, comfortably under a 200ms API budget.

The graph that Neo4j is optimized for — massive, densely connected, with multi-hop traversals hitting millions of nodes — is a problem most engineering teams won't have for years. And by then, the query patterns and scale characteristics will be much clearer.

**Operational cost compounds fast**

Adding a second persistence engine means two connection pools, two backup strategies, two operational runbooks, two sets of skills your on-call rotation needs at 3am. For a bootstrapped SaaS with one infrastructure engineer (me), that's a very real cost.

PostgreSQL is already the primary store for all other domains. Everything is already Flyway-migrated, RLS-isolated by tenant, and OTLP-traced. The same applies to graph data. One Postgres cluster, one concern.

**Recursive CTEs are not that scary**

```sql
WITH RECURSIVE blast_radius AS (
  SELECT target_id AS service_id, 1 AS depth
  FROM   dependencies
  WHERE  source_id = :serviceId
    AND  deleted_at IS NULL
  UNION ALL
  SELECT d.target_id, br.depth + 1
  FROM   dependencies d
  JOIN   blast_radius br ON br.service_id = d.source_id
  WHERE  d.deleted_at IS NULL
    AND  br.depth < 10          -- depth guard prevents runaway traversals
)
SELECT DISTINCT service_id FROM blast_radius;
```

This is readable, auditable, and performable. It's also indexed — `(source_id)` and `(target_id)` on the `dependencies` table make each CTE step a fast index lookup.

**When would I reconsider?**

At 100k+ edges with multi-hop traversal queries consistently hitting the 500ms wall, I'd evaluate Apache AGE (a graph extension for PostgreSQL that avoids the operational split) before jumping to a dedicated graph database. If AGE couldn't close the gap, I'd migrate the topology service only, keeping all other services on PostgreSQL.

The point: start with one operational concern. Specialize only when the actual data proves it's necessary.

## LinkedIn Article

**Title:** The graph database I didn't add — and the SQL I used instead

When designing Cartogra's topology layer, the data model looked like a textbook graph problem. Services are nodes. Dependencies are edges. Blast radius, cycle detection, and ancestry queries are classic graph traversals. The obvious move: add a dedicated graph database.

The move I made instead: PostgreSQL with recursive CTEs.

**Why it works**

PostgreSQL's `WITH RECURSIVE` clause handles all the traversal patterns a service catalog needs — blast radius, cycle detection, transitive dependencies — with predictable performance at realistic scale (tens to hundreds of services, thousands of edges).

The key is a proper index on the `dependencies` table: `(source_id)` and `(target_id)` turn each CTE step into a fast index lookup. Add a depth guard (`WHERE depth < 10`) and you prevent runaway traversals. The result is sub-50ms query times at current scale.

**The operational argument**

Every new persistence engine adds operational surface area: another backup strategy, another connection pool tuning session, another page at 3am. For a small team building a bootstrapped product, that compound cost is real. PostgreSQL is already the primary store for all other domains. Keeping graph data there means one operational concern, not two.

**The reversal condition**

This is not a permanent decision. ADR-0001 documents exactly when we'd reconsider: 100k+ edges with traversal queries consistently over 500ms. The migration path is Apache AGE first (graph extension on PostgreSQL), then a dedicated graph database only if AGE can't close the gap.

Decision-making is better when the reversal conditions are explicit. What scale would force you to reconsider an architectural choice you made last year?
