# ADR-0017 — Audit events: owning service and `AuditEventPort` shape

**Status**: Proposed
**Date**: 2026-05-20
**Deciders**: Allan Weber

---

## Context

Phase 2 introduces an `audit_events` table (task 2.34) and an `AuditEventPublisher` populated from all mutating use cases across registry, topology, and contract (task 2.35). Two architectural problems with the original wording:

1. **Owning service unspecified**. "Check existing migration files to determine the correct version number for the owning service" doesn't say which service owns the table.
2. **`shared:common` cannot host a JDBC writer**. CLAUDE.md is explicit: `shared:common` is plain Java only, zero Spring dependencies. A class that writes audit rows to PostgreSQL needs JDBC and Spring's transaction manager — it cannot literally live in `shared:common`.

The audit identified this as **dead-end 7** in the phase 1–5 review.

The constraints to satisfy:

- One canonical store of audit rows for the whole tenant.
- All mutating use cases across registry, topology, contract (and later, intelligence) must reliably record audit data.
- `shared:common` stays Spring-free.
- The GDPR erasure flow (task 3.41) needs to anonymise rows; a single owning service simplifies that scope.

---

## Decision

**Registry owns the `audit_events` table.** All audit rows land in the registry database.

**`shared:common` defines an `AuditEventPort` interface** — plain Java, no Spring. Shape:

```java
public interface AuditEventPort {
    void record(AuditEvent event);
}

public record AuditEvent(
    UUID tenantId,
    String entityType,
    UUID entityId,
    String action,
    UUID actorId,
    Map<String, Object> payload
) {}
```

**Each service ships its own adapter:**

| Service | Adapter | Write path |
|---------|---------|------------|
| registry | `JdbcAuditEventAdapter` | Direct `INSERT INTO audit_events` via `NamedParameterJdbcTemplate`, same transaction as the mutating use case. |
| topology | `KafkaAuditEventAdapter` | Publish `cartogra.audit.recorded` envelope (eventType `audit.recorded`). |
| contract | `KafkaAuditEventAdapter` | Same as topology. |
| intelligence (Phase 4) | `KafkaAuditEventAdapter` | Same as topology. |

**Registry consumes `cartogra.audit.recorded`** (task 2.35a) and persists incoming envelopes idempotently keyed on `eventId` (the UUIDv5 generated by `EventEnvelope.of`).

The choice between in-transaction (registry) and async (everyone else) is deliberate: the registry needs same-transaction guarantees for its own writes (otherwise an audit gap is possible during partial failure), while cross-service audit is an at-least-once async stream by nature.

---

## Consequences

### Positive

- `shared:common` stays Spring-free, satisfying CLAUDE.md.
- Single audit store simplifies GDPR erasure (task 3.41), audit query API (task 2.37), and exports.
- Non-owning services don't take a hard dependency on registry's database or REST surface — they publish a Kafka envelope and move on.
- The `AuditEventPort` interface is reusable in tests via a simple in-memory adapter.

### Negative / Trade-offs

- Cross-service audit rows are at-least-once via Kafka, not transactional. A topology mutation that succeeds but whose audit publish fails leaves an audit gap. Mitigation: the existing transactional-outbox pattern (task 3.17) could be reused; recommended as a Phase 3 hardening, not Phase 2 blocker.
- The registry service grows a new responsibility (consuming audit envelopes). The work is small (one consumer, one INSERT), but the cognitive boundary moves.

### Neutral

- The `audit_events` table is owned by registry but written to from anywhere via the port. The migration in 2.34 lives in `services/registry/src/main/resources/db/migration/`.

---

## Alternatives Considered

| Option | Reason rejected |
|--------|-----------------|
| Per-service `audit_events` tables | Multiplies the GDPR scope (3.41 must anonymise N tables) and the audit-query implementation (2.37 must federate across services). |
| `AuditEventPublisher` lives in `shared:common` as concrete code | Violates the zero-Spring-deps rule. Would force `shared:common` to gain JDBC + Spring TX, dragging the dependency cost into every consumer of `shared:common`. |
| A new dedicated `audit` microservice | Out of scope for Phase 2; would multiply the service count without proportional value. |
| Synchronous REST from non-registry services to registry's audit endpoint | Couples mutating writes in topology/contract to registry availability; if registry is down, mutations block. Kafka decouples this. |
