# Plan: Registry Domain & API — Items 1.3–1.15

## Context

The registry service has Phase 0 infrastructure in place (4 Flyway migrations for tenants/teams/users/SCM connections, a `PingController`, `GlobalExceptionHandler`, and 3 integration tests) but no domain code. Items 1.3–1.15 build the full registry domain: hexagonal package structure, 3 new migrations, JDBC repositories for all entities, domain use cases, REST controllers, integration tests, and two ADRs with BIP drafts.

This is too large for one PR. Splitting into **two PRs** keeps each reviewable and lets the domain layer land before the HTTP surface.

## PR 1 — Registry Domain Foundation (1.3, 1.4–1.6, 1.7, 1.8, 1.9)

### 1.3 — Hexagonal package structure

Reorganize `services/registry/src/main/java/io/cartogra/registry/` into:

```
registry/
├── api/           # (already exists — controllers, DTOs, mappers, GlobalExceptionHandler)
├── application/   # use case interfaces + DTOs
│   ├── dto/
│   └── usecase/
├── domain/        # entities, value objects, domain enums
├── infrastructure/# JDBC repos, Kafka producers
│   ├── jdbc/
│   └── kafka/
└── config/        # (already exists — Spring beans, OTel)
```

Existing files stay in place (`api/`, `config/`). No Spring dependencies in `domain/` or `application/` — those must be Spring-free.

### 1.4 — V005__create_services.sql

`services/registry/src/main/resources/db/migration/V005__create_services.sql`

```sql
CREATE TABLE services (
    id               UUID        NOT NULL DEFAULT gen_random_uuid() PRIMARY KEY,
    tenant_id        UUID        NOT NULL,
    name             TEXT        NOT NULL,
    description      TEXT,
    team_id          UUID,                    -- nullable; null = orphan
    repository_url   TEXT,
    tech_stack       JSONB,                   -- detected build files/frameworks
    metadata         JSONB,
    health_status    TEXT        NOT NULL DEFAULT 'unknown',  -- healthy | degraded | unknown
    last_deployed_at TIMESTAMPTZ,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at       TIMESTAMPTZ
);

CREATE INDEX ON services (tenant_id) WHERE deleted_at IS NULL;
CREATE INDEX ON services (tenant_id, team_id) WHERE deleted_at IS NULL;
CREATE INDEX ON services USING GIN (tech_stack) WHERE tech_stack IS NOT NULL;
CREATE INDEX ON services USING GIN (metadata) WHERE metadata IS NOT NULL;
-- Full-text search on name + description
CREATE INDEX ON services USING GIN (to_tsvector('english', coalesce(name,'') || ' ' || coalesce(description,'')));

ALTER TABLE services ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON services
    USING (tenant_id = current_setting('app.current_tenant_id')::UUID);
```

### 1.5 — V006__create_services_history.sql

`services/registry/src/main/resources/db/migration/V006__create_services_history.sql`

Append-only temporal snapshot table — one row per material change.

```sql
CREATE TABLE services_history (
    id          UUID        NOT NULL DEFAULT gen_random_uuid() PRIMARY KEY,
    service_id  UUID        NOT NULL,
    tenant_id   UUID        NOT NULL,
    snapshot    JSONB       NOT NULL,   -- full service row at point-in-time
    changed_by  UUID,                  -- user_id (nullable for system changes)
    changed_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX ON services_history (service_id, changed_at DESC);
CREATE INDEX ON services_history (tenant_id, changed_at DESC);

ALTER TABLE services_history ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON services_history
    USING (tenant_id = current_setting('app.current_tenant_id')::UUID);
```

### 1.7 — JDBC Repositories

**Domain entities** (Spring-free records in `domain/`):
- `Service.java` — maps services table; `healthStatus` as `ServiceHealthStatus` enum
- `ServiceSnapshot.java` — maps services_history row
- `Team.java` — maps existing teams table
- `ScmConnection.java` — maps existing scm_connections table

**Application-layer repository interfaces** (Spring-free, in `application/`):
- `ServiceRepository` — findById, findAll (with filters), save, softDelete, findOrphaned, countByTeam
- `ServiceHistoryRepository` — save (snapshot), findByServiceId (paged), findAtPointInTime
- `TeamRepository` — findById, findAll, save, softDelete
- `ScmConnectionRepository` — findById, findAll, save, softDelete

**Infrastructure JDBC implementations** (in `infrastructure/jdbc/`):
- `JdbcServiceRepository` — uses `NamedParameterJdbcTemplate`; explicit SQL with `:param` binding; filtering by team, health, tech_stack, full-text search
- `JdbcServiceHistoryRepository`
- `JdbcTeamRepository`
- `JdbcScmConnectionRepository`

All JDBC repos filter by `tenant_id` on every query. No unbounded queries — all list queries accept a `PageRequest` or explicit `limit/offset`.

### 1.8 — Use Cases

Use case interfaces in `application/usecase/`; implementations in `application/usecase/impl/` (Spring `@Component`):

| Interface | Key behavior |
|-----------|-------------|
| `CreateServiceUseCase` | Validate name uniqueness per tenant, persist, emit history snapshot |
| `UpdateServiceUseCase` | Validate, update, persist history snapshot on every call |
| `DeleteServiceUseCase` | Soft-delete (set `deleted_at`), persist history snapshot |
| `FindServiceUseCase` | findById (throws `ServiceNotFoundException` if absent or soft-deleted) |
| `ListServicesUseCase` | Filter by team, health, tech_stack array, full-text search; paged |
| `AssignOwnerUseCase` | Set `team_id`; validates team belongs to same tenant |
| `DetectOrphansUseCase` | Returns services where `team_id IS NULL` or team is soft-deleted |
| `GetServiceHistoryUseCase` | Returns paged snapshots from `services_history`; supports point-in-time by timestamp |

DTOs live in `application/dto/` (records). No Jackson or Spring annotations in application layer.

### 1.9 — services_history Snapshot

`UpdateServiceUseCase`, `CreateServiceUseCase`, and `DeleteServiceUseCase` implementations call `ServiceHistoryRepository.save()` after every successful mutation. The snapshot is the full `Service` record serialized to JSONB. This happens within the same transaction as the mutation.

## PR 2 — Registry API, Tests & Docs (1.10–1.15)

### 1.10 — REST Controllers + Error Handling

**Controllers** in `api/controller/`:

| Controller | Routes |
|-----------|--------|
| `ServiceController` | `GET/POST /api/v1/services`, `GET/PUT/DELETE /api/v1/services/{id}`, `GET /api/v1/services/orphaned`, `GET /api/v1/services/{id}/history` |
| `TeamController` | `GET/POST /api/v1/teams`, `GET/PUT/DELETE /api/v1/teams/{id}` |
| `ScmConnectionController` | `GET/POST /api/v1/scm-connections`, `GET/PUT/DELETE /api/v1/scm-connections/{id}` |

All controllers:
- Take `@RequestHeader("X-Tenant-Id") UUID tenantId` (injected by gateway in prod; used directly in tests)
- Return `ResponseEntity<ApiResponse<T>>` from `shared:common`
- Set `X-Trace-Id` header using `Span.current().getSpanContext().getTraceId()`
- Use `@Valid` on request bodies

**Expand `GlobalExceptionHandler`** to add stable error codes:
- `ServiceNotFoundException` → 404 `SERVICE_NOT_FOUND`
- `TeamNotFoundException` → 404 `TEAM_NOT_FOUND`
- `DuplicateServiceNameException` → 409 `CONFLICT`
- `TenantMismatchException` → 403 `FORBIDDEN`

DTOs (request/response records) in `api/dto/`; mappers in `api/mapper/`.

### 1.11 — Testcontainers Integration Tests

Test class per major flow in `src/test/java/io/cartogra/registry/`:
- `ServiceCrudIT` — create, read, update, soft-delete, 404 on missing/deleted
- `ServiceHistoryIT` — update → history row exists; point-in-time query returns correct snapshot
- `OrphanDetectionIT` — assign team, unassign team → appears in `/orphaned`
- `EnvelopeAndHeaderIT` — all responses have `data`/`error` + `traceId` body field + `X-Trace-Id` header
- `FlywayMigrationSmokeTest` — update existing test to also assert V005, V006, V007 tables exist

All ITs use `PostgresTestSupport.POSTGRES` from `shared:test-support` with `@DynamicPropertySource`.

### 1.12 — ADR: PostgreSQL + Recursive CTEs

Check ADR-0001 scope first. ADR-0001 covers "PostgreSQL over graph DB" at a high level. If it lacks CTE-specific content (query strategy, bounded depth, path-explosion guards), **extend ADR-0001** with a new section rather than creating a duplicate. If ADR-0001 needs no update, mark 1.12 as satisfied by it. Document this decision in the PR description.

If a new ADR is warranted: `docs/adr/ADR-0004-postgresql-recursive-ctes-graph-queries.md` following existing format.

`docs/bip/1.13-postgresql-vs-graph-db.md`

All 5 channels (blog, Twitter/X thread, Instagram carousel, LinkedIn, optional video outline). Focus: the pragmatic case for PostgreSQL + CTEs over Neo4j/DGraph for a bootstrapped SaaS. Tie to the actual ADR content.

### 1.14 — ADR: Spring Data JDBC

`docs/adr/ADR-0004-spring-data-jdbc.md` (or ADR-0005 if 0004 is used for CTEs)

Covers: why Spring Data JDBC over JPA/Hibernate; aggregate-root discipline; explicit SQL transparency; Spring Boot 4 compatibility; trade-offs (no lazy loading, no L2 cache).

### 1.15 — BIP: Spring Data JDBC

`docs/bip/1.15-spring-data-jdbc-rationale.md`

All 5 channels. Focus: why explicit SQL beats ORM magic for a multi-tenant, audit-heavy domain. Engineers who've been burned by JPA LazyInitializationException are the target audience.
