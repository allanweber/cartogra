# Plan: Tasks 1.45–1.46 — Contract Tests and Registry OpenAPI Update

## Feature Summary

Task 1.45 adds a dedicated contract-test suite that exhaustively verifies every registry and gateway response
conforms to the shared API envelope (`{ data, traceId }` / `{ error, traceId }`) and the `X-Trace-Id` header
contract. Responses are validated against the actual OpenAPI spec file using
`com.atlassian.oai:swagger-request-validator-core` — the servlet-free validation engine that works under
Spring Boot 4 / Jakarta EE 11. Task 1.46 brings `docs/api/registry.openapi.yaml` into full alignment with
the implemented surface, including missing 429 responses and any field-level discrepancies. Together they
close the Phase 1 contract gap before the BIP/publish tasks begin.

#### E2E Test Strategy (PR body)

**Prerequisites:**
- Docker Compose up with Postgres and Redis healthy
- `./gradlew build` from repo root passes

**Steps:**

1. `./gradlew :services:registry:test` — all tests green, including new `RegistryEnvelopeContractTest`
2. `./gradlew :services:gateway:test` — all tests green, including new `GatewayEnvelopeContractTest`
3. Start the registry directly: `./gradlew :services:registry:bootRun`
4. Send `POST http://localhost:8081/api/v1/services` with `X-Tenant-Id` header:
   - Assert response body has `.data` and `.traceId`
   - Assert `X-Trace-Id` response header equals `.traceId`
   - Assert `.traceId` is exactly 32 lowercase hex characters
5. Send `GET http://localhost:8081/api/v1/services/{random-uuid}` (non-existent):
   - Assert status 404
   - Assert response body has `.error.code == "NOT_FOUND"` and `.traceId`
   - Assert `X-Trace-Id` header equals `.traceId`
6. Open `docs/api/registry.openapi.yaml` in Stoplight or run `redocly lint` — no errors
7. Confirm every endpoint in the spec shows a 429 response

**Passing signal:** All assertions in steps 4–7 succeed.

**Failure triage:**
- `traceId` is missing/null: check `GlobalExceptionHandler` and `ServiceController` — ensure
  `Span.current().getSpanContext().getTraceId()` is called after OTel is initialised
- `X-Trace-Id` header absent: check `ResponseEntity` builder call in the controller and the
  exception handler's `HttpHeaders` population
- `traceId` not 32 hex: OTel returns `"0000...0000"` when there is no active span — ensure
  the test context has a real Testcontainers Postgres running so OTel auto-instrumentation fires

### Task 1.46 — Update registry OpenAPI spec

**What to build:** Audit `docs/api/registry.openapi.yaml` against the implemented controllers and
DTOs; add missing 429 responses to every path operation; verify every response schema field matches
the actual Java records; clarify the `/ci/check` envelope behavior in the spec description.

**Files to create or modify:**

| File | Action | Notes |
|------|--------|-------|
| `docs/api/registry.openapi.yaml` | Modify | Add 429 responses, verify schema fields, clarify CI endpoint |

**Changes to make:**

1. **Add 429 response to every operation.** Every `GET`, `POST`, `PATCH`, `DELETE` path operation
   should gain:
   ```yaml
   '429':
     description: Too many requests — rate limit exceeded (enforced at the gateway)
     content:
       application/json:
         schema:
           $ref: '#/components/schemas/ApiErrorResponse'
     headers:
       X-Trace-Id:
         $ref: '#/components/headers/X-Trace-Id'
   ```
   Note: rate limiting is enforced by the gateway, but documenting 429 here covers direct registry
   calls behind the gateway as well.

2. **Verify service response fields.** Cross-check `ServiceResponse.java` fields against the
   `ServiceDto` / `ServiceResponse` schema in the spec:
   - Confirm `healthStatus`, `tier`, `language`, `teamId`, `repositoryUrl`, `specUrl`, `tags`
     are all present in the spec schema
   - Confirm `deletedAt` is NOT exposed in the response (soft-delete field must be internal)

3. **Verify team response fields.** Cross-check `TeamResponse.java` against `TeamDto` schema —
   confirm `slackChannel` and `oncallRotation` fields are present.

4. **Verify SCM connection response fields.** Cross-check `ScmConnectionResponse.java` against the
   spec — confirm `provider`, `repositoryUrl`, `branch`, `lastSyncedAt` are present.

5. **Clarify `/ci/check` envelope.** The current spec marks this endpoint's 200 response as a
   raw `CiCheckResult` (not wrapped). Verify against `CiController.java`: if the controller uses
   `ApiResponse<CiCheckResult>`, update the spec to show the wrapper; if it returns the result
   directly, add a `description` note explaining the intentional deviation.

**Critical constraints:**
- Do not change existing schema `$ref` names — downstream consumers may reference them
- Keep the spec as OpenAPI 3.1.0 (already set)

### Task 1.45 — Registry and gateway API envelope contract tests

**What to build:** A shared `OpenApiContractValidator` test utility backed by
`swagger-request-validator-core`, plus two test classes that drive it.
`RegistryEnvelopeContractTest` covers all three registry controllers (services, teams, SCM connections).
`GatewayEnvelopeContractTest` covers gateway-owned error paths (auth failures, rate-limit).

**New dependency — add to `shared/test-support/build.gradle.kts` and both service test classpaths:**

```kotlin
// shared/test-support/build.gradle.kts
testImplementation("com.atlassian.oai:swagger-request-validator-core:2.46.0")
```

The `*-core` artifact is the pure validation engine — no `javax.servlet` / `jakarta.servlet` imports,
compatible with Spring Boot 4.

> **OpenAPI 3.1 caveat:** `swagger-request-validator-core` parses specs via `swagger-parser` which has
> partial 3.1 support (nullable via `type: ["string","null"]` works; some 3.1-only keywords like
> `unevaluatedProperties` are silently ignored). The registry spec uses standard 3.1 constructs that
> are all handled correctly. If the validator rejects valid 3.1 syntax, downgrade the affected schema
> to 3.0-compatible equivalents (e.g. replace `type: ["string","null"]` with `nullable: true`).

**Key signatures:**

```java
// shared/test-support — OpenApiContractValidator.java
public final class OpenApiContractValidator {

    private final OpenApiInteractionValidator validator;

    public OpenApiContractValidator(String specClasspathUrl) {
        this.validator = OpenApiInteractionValidator
            .createForSpecificationUrl(specClasspathUrl)
            .build();
    }

    /**
     * Validates that the actual HTTP response body and headers conform to the spec for the
     * given path+method+status. Fails the test immediately if the report contains errors.
     */
    public void assertResponse(String method, String path, int status,
                               String body, Map<String, String> headers) {
        var response = SimpleResponse.Builder.status(status)
            .withBody(body)
            .withHeaders(headers)
            .build();
        var report = validator.validateResponse(path, Method.valueOf(method.toUpperCase()), response);
        assertThat(report.hasErrors())
            .as("OpenAPI contract violations for %s %s → %d:\n%s", method, path, status, report)
            .isFalse();
    }
}
```

```java
// Registry tests — helper that wraps HttpResponse into the validator call
private final OpenApiContractValidator contractValidator =
    new OpenApiContractValidator("classpath:registry.openapi.yaml");

private void assertConformsToSpec(String method, String path,
                                   HttpResponse<String> response) throws Exception {
    Map<String, String> headers = response.headers().map().entrySet().stream()
        .collect(Collectors.toMap(Map.Entry::getKey, e -> e.getValue().getFirst()));
    contractValidator.assertResponse(method, path, response.statusCode(), response.body(), headers);

    // Additional X-Trace-Id ↔ body traceId consistency check (not covered by schema validation)
    JsonNode root = objectMapper.readTree(response.body());
    String traceId = root.has("traceId") ? root.get("traceId").asText()
                   : root.path("error").path("traceId").asText("");
    assertThat(traceId).matches("[0-9a-f]{32}");
    assertThat(response.headers().firstValue("X-Trace-Id")).hasValue(traceId);
}
```

```java
// Gateway tests — helper that wraps MockMvc MvcResult
private final OpenApiContractValidator contractValidator =
    new OpenApiContractValidator("classpath:gateway-errors.openapi.yaml");

private void assertConformsToSpec(String method, String path, MvcResult result) throws Exception {
    MockHttpServletResponse r = result.getResponse();
    Map<String, String> headers = r.getHeaderNames().stream()
        .collect(Collectors.toMap(h -> h, r::getHeader));
    contractValidator.assertResponse(method, path, r.getStatus(),
        r.getContentAsString(StandardCharsets.UTF_8), headers);

    // X-Trace-Id ↔ body traceId consistency
    JsonNode root = objectMapper.readTree(r.getContentAsString(StandardCharsets.UTF_8));
    String traceId = root.path("traceId").asText("");
    assertThat(traceId).matches("[0-9a-f]{32}");
    assertThat(r.getHeader("X-Trace-Id")).isEqualTo(traceId);
}
```

  `processTestResources` dependency chain
- The `traceId` header consistency assertion (`X-Trace-Id` == body `traceId`) is added on top of the
  spec validation because header values are not cross-validated by the core library
