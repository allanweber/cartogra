#### Blog post (600–1000 words)

**Title:** Every API Response Carries a Trace ID — Here's Why, and How

The first time I lost 45 minutes debugging a production API error, the problem was simple: the
response said "something went wrong" and gave me nothing else. No request ID. No correlation.
Nothing to grep for in the logs.

That experience drove one early Cartogra decision: every API response carries a trace ID.
Not as an afterthought — as a first-class field in the response envelope.

**The envelope format**

Every response from every Cartogra service wraps its payload in a two-field envelope:

```json
{
  "data": { "id": "...", "name": "payment-service", ... },
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

Errors follow the same shape:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Service with id abc not found",
    "details": {}
  },
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

The `traceId` is always present, always a 32-character lowercase hex string — the OpenTelemetry
W3C trace ID format. The same value appears in the `X-Trace-Id` response header.

**Where the ID comes from**

Cartogra uses OpenTelemetry with Spring Boot's auto-instrumentation. Every inbound HTTP request
starts a new OTel span. Extracting the trace ID takes exactly one line:

```java
String traceId = Span.current().getSpanContext().getTraceId();
```

That ID is added to every response body and every response header. The log line for the same
request also carries `traceId` as a structured field. One ID, three places: body, header, log.

**Why the `X-Trace-Id` header duplicates the body**

Because API consumers often check headers before parsing JSON. A monitoring tool, a CDN, a test
assertion — all of them can read `X-Trace-Id` without deserializing the body. Duplicating it
costs nothing and makes a narrow class of integrations dramatically simpler.

The contract is enforced by test: `GatewayEnvelopeContractTest` and `RegistryEnvelopeContractTest`
assert that every response — 2xx and 4xx alike — has both fields, and that they match.

**What the traceId actually unlocks**

When a user files a support request, they paste the `traceId` from the error message the frontend
surfaced. We grep for it in the LGTM/Loki log pipeline. Every log line from gateway → registry →
topology that participated in that request carries the same ID. The entire call graph for that
one request is instantly visible — no log archaeology, no timeline stitching.

For the platform team, the trace goes further: the same ID connects to the Tempo distributed
trace, showing exactly which span was slow or failed and what the downstream service returned.

**The W3C `traceparent` header propagates it downstream**

The gateway doesn't just add the ID to the response — it propagates it forward. Every
`RestClient` call to a downstream service includes the W3C `traceparent` header:

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

Every Kafka message includes it as a message header. OTel auto-instrumentation picks it up on
the receiving end and continues the same trace. One request, one ID, across every hop.

**The anti-pattern this avoids**

The alternative — returning a raw response body without an ID — forces every debugging session
to rely on approximate log timestamps. "The error happened around 14:32" leads to "grep for
that path around that time" which leads to "which of these fifteen requests was it?" The envelope
eliminates that class of question entirely.

If you're building an API and you're not including a correlation ID in every response, add it
now. The implementation is four lines. The operational return is significant.

#### Blog post (600–1000 words)

**Title:** Why Auth Lives in the Gateway — and Nowhere Else

The most common mistake I see in Spring microservice tutorials: adding `spring-boot-starter-security`
to every service and having each one validate JWTs independently. It's the path of least resistance
and a long-term maintenance problem.

Cartogra made the opposite choice. Auth lives in the gateway. The five other backend services don't
touch a token.

Here's the reasoning, the implementation, and the OAuth integration strategy.

**The per-service auth trap**

When every service validates tokens independently, the operational surface area compounds quietly:

- JWT secret rotation requires a coordinated redeploy of every service simultaneously.
- Rate limiting before credential validation requires every service to implement it — or you do it
  inconsistently.
- A new OAuth provider means updating auth logic in five places.
- One service running a stale JWT library version creates a silent security divergence.

These costs are low in the first month. They accumulate over quarters.

**The gateway as the perimeter**

In Cartogra, the `gateway` service (port 8080) is the only component that issues and validates
JWTs. The Spring Cloud Gateway routing layer and Spring Security 7 ReactiveSecurityContextHolder sit
in the same process. Rate limiting, auth, and routing share one Redis connection pool. Tenant context
injection happens once, immediately after token validation, and is propagated to downstream services
via injected headers — not re-derived.

Downstream services (registry, topology, contract) receive `X-Tenant-Id` and `X-User-Id` headers
injected by the gateway's `TenantInjectionGlobalFilter`. They never see a token. They cannot forge
one. In production, Kubernetes NetworkPolicy adds a second enforcement layer.

This is documented in ADR-0010: the gateway is the sole token issuer for MVP scope. When auth
complexity grows past what a single gateway can manage — SCIM provisioning, device flow, federated
identity — the use-case boundaries (`RegisterUserUseCase`, `LoginUseCase`) are clean enough to
extract to a dedicated auth service without touching the downstream services at all.

**Dual-mode: cookie for browsers, Bearer for API clients**

Browsers and API clients have fundamentally different constraints:

- A browser can't easily attach an `Authorization: Bearer` header to a form submit or a redirect.
  But it can automatically send an `httpOnly; Secure; SameSite=Lax` cookie — one that JavaScript
  cannot read (XSS cannot steal it).
- A CI pipeline or CLI tool can't handle cookies. It needs a raw token for the `Authorization`
  header.

The solution is to issue the same JWT and deliver it two ways on login. The `AuthController` sets
an `httpOnly` cookie AND returns the token in the response body:

```java
response.addCookie(ResponseCookie.from("jwt", tokens.accessToken())
    .httpOnly(true).secure(true).sameSite("Lax").path("/")
    .maxAge(tokens.expiresIn()).build());
// Body also has access_token for API clients
return ResponseEntity.ok(new ApiResponse<>(tokens, traceId));
```

The filter tries cookie extraction first, then `Authorization: Bearer`. Cookie takes precedence —
it matches browser behavior without penalising API clients.

A third mode exists for CI pipelines: `X-Cartogra-Api-Key`, a tenant-scoped API key that bypasses
JWT entirely. Same security boundary, different credential type. This is ADR-0011.

**OAuth integration strategy**

OAuth providers (Google, GitHub, GitLab) are supported via Spring Security 7's reactive OAuth2 client.
The gateway handles the OIDC authorization code flow end-to-end: redirect to provider, receive the
code, exchange for an ID token, validate claims, and issue a Cartogra JWT.

The key decision: we issue a Cartogra JWT after OAuth, rather than forwarding the provider token.
Provider tokens have variable expiry, variable claim shapes, and no `tid` (tenant ID) claim.
Cartogra needs a consistent JWT with `{ sub, tid, roles[], exp }` regardless of how the user
authenticated. The OAuth provider becomes an identity source, not a token issuer.

The OAuth state is stored in Redis with a short TTL — one round trip, no persistent DB write for
the handshake. The mapping from provider identity to Cartogra user is in PostgreSQL.

**The enforcement gap that gets missed**

One pattern that looks like it works but doesn't: stripping `X-Tenant-Id` from inbound client
requests at the gateway but not re-injecting it from the token. If you forget the re-injection,
services that trust the header get no tenant context and either throw or return data for the wrong
tenant.

The Cartogra `TenantInjectionGlobalFilter` does both in one step: strip the inbound header, then
add the header derived from the validated JWT `tid` claim. One filter, one place, enforced on every
proxied request.

#### Blog post (600–1000 words)

**Title:** The Registry That Reads the Git Repo and Fixes Itself

Every service catalog I've seen has the same long-term failure mode: it starts accurate and drifts.
Engineers update code, forget to update the catalog. Teams change, ownership records go stale. A
new service gets deployed without ever being registered.

Cartogra's answer to catalog drift is not a better form. It's a sync pipeline.

**The drift problem**

Manual registration is optimistic. It assumes engineers will remember to update a catalog entry
when they rename a service, change its owner, or update its OpenAPI spec. In practice, the catalog
is accurate on the day it's populated and degrades from there.

The catalog that's 80% accurate is in some ways worse than no catalog. You can't trust it, so you
don't use it for blast radius analysis or dependency decisions. But it's still there, appearing
authoritative, accumulating stale data.

**The SCM is the source of truth**

Every service that matters lives in a Git repository. The repository has:

- A `service.yaml` (or equivalent) describing the service name, tier, and language
- A `CODEOWNERS` file mapping paths to team ownership
- An OpenAPI spec at a known path (or a `specUrl` in `service.yaml` pointing to one)

If the SCM already has this data, the catalog shouldn't require engineers to enter it again. It
should read it.

**The sync pipeline**

Cartogra's ingestion service runs a sync worker that, given a registered SCM connection, does this:

1. Lists all repositories for the tenant's GitHub organization or Azure DevOps project
2. For each repository, fetches `service.yaml`, `CODEOWNERS`, and the spec URL
3. Upserts the service record in the registry (create if new, update if changed, soft-delete if
   the repo was archived)
4. Resolves team ownership from CODEOWNERS and creates or updates team records
5. Emits a `cartogra.registry.service.synced` Kafka event for downstream consumers

The sync command is idempotent: running it twice produces the same result. If a field hasn't
changed, the `updated_at` timestamp is not bumped. This is enforced at the use-case layer before
the database write (ADR-0014).

**The SPI abstraction**

GitHub and Azure DevOps have completely different APIs, auth models, and repository hierarchies.
Rather than putting provider-specific logic in the use case, Cartogra defines a `ScmProvider`
interface:

```java
public interface ScmProvider {
    String providerType();
    List<ScmRepository> listRepositories(ScmConnectionConfig config);
    Optional<String> getFileContents(ScmConnectionConfig config, String repoPath, String filePath);
    OwnershipMap resolveOwnership(ScmConnectionConfig config, ScmRepository repository);
}
```

`GitHubProvider` and `AzureDevOpsProvider` implement it. The use case doesn't know what GitHub
is — it dispatches by provider type string. Adding GitLab means implementing `ScmProvider` and
annotating with `@Component`. No use-case code changes.

Credentials are passed per-call from the `scm_connections` table (stored as JSONB), not as env
vars. The ingestion service doesn't hold secrets between syncs.

**The "self-healing" property**

Here's the key: the sync is continuous, not one-shot. A webhook receiver in the ingestion service
triggers a targeted sync on every push to a registered repository. A scheduled sync catches
repositories that don't send webhooks.

When an engineer renames a service in `service.yaml`, the next webhook push triggers a sync.
The registry updates. No human action required. The catalog heals itself from the SCM truth.

When a repo is archived, the next sync soft-deletes the service record. When `CODEOWNERS` changes,
team ownership updates. When the spec URL changes, the contract service picks up the new spec on
its next validation run.

The catalog is only as stale as the most recent SCM event. For active repositories, that's seconds.

**What it doesn't solve**

Services that don't live in a registered SCM connection still require manual registration. The sync
pipeline extends trust to the boundary of the tenant's registered SCM accounts — not beyond it.
Similarly, services with no `service.yaml` won't be auto-discovered. The file is the contract
between the service team and the catalog.

The long-term answer for the first problem is a CI/CD integration that automatically registers a
service on its first successful deploy. That's a later phase. The sync pipeline is the foundation
it builds on.

#### Blog post (600–1000 words)

**Title:** Multi-Tenancy and History Tables: The Data Model Decisions That Age Well

When you're building a SaaS product, two decisions you make in the first month will echo across
every feature you build for the next two years: how you isolate tenant data, and how you record
the history of changes. Get both wrong and you'll be rewriting your schema in production under
live traffic. Get them right and they become invisible infrastructure that makes everything else
easier.

Here's how Cartogra approaches both.

**Multi-tenancy: isolation by column, enforced by policy**

Every domain table in Cartogra has `tenant_id UUID NOT NULL`. Not most tables — every table, no
exceptions. This is enforced as a lint rule in the `check-constraints` slash command and verified
during code review.

Queries filter by `tenant_id` at the repository layer. But column-level filtering alone can be
defeated by a bug — a join that forgets the `WHERE tenant_id = :tenantId` clause, for example.
PostgreSQL's Row Level Security (RLS) adds a second enforcement layer:

```sql
ALTER TABLE services ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON services
    USING (tenant_id = current_setting('app.current_tenant_id')::UUID);
```

The RLS policy is a safety net, not the primary mechanism. The primary mechanism is the
application-level filter. RLS catches bugs that slip past review.

**How tenant identity flows through the system**

The JWT issued by the gateway carries a `tid` claim (tenant ID). The gateway's
`TenantInjectionGlobalFilter` strips inbound `X-Tenant-Id` headers from clients (a client
cannot forge their tenant context) and re-injects the value from the validated token. Downstream
services trust the injected header — they never decode a token.

Redis keys are prefixed: `tenant:{tenantId}:rate-limit:...`. No cross-tenant cache collision is
possible if this prefix is applied consistently. A project-wide Grep for Redis key construction
is part of the Phase 1 audit checklist.

**Temporal versioning: the history table pattern**

Soft deletes (`deleted_at TIMESTAMPTZ`) are table stakes — hard deletes make debugging and audit
impossible. But soft deletes only tell you that a record was deleted, not what it looked like
before. For a service registry, that's often not enough.

Cartogra adds a `service_history` table for point-in-time queries:

```sql
CREATE TABLE service_history (
    id            UUID        NOT NULL DEFAULT gen_random_uuid() PRIMARY KEY,
    service_id    UUID        NOT NULL,
    tenant_id     UUID        NOT NULL,
    changed_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    changed_by    UUID,
    change_type   TEXT        NOT NULL, -- CREATED | UPDATED | DELETED
    snapshot      JSONB       NOT NULL
);
```

On every mutation (create, update, soft-delete), the use case writes a new history row with a
JSONB snapshot of the service state at that moment. The history table is append-only — it is
never updated or soft-deleted. It's a log, not a mutable record.

This enables queries like: "What did `payment-service` look like six months ago?" — answered by
selecting the most recent history row before the target timestamp.

**Ownership history**

Team ownership changes over time. The `team_id` foreign key on `services` captures the current
owner. But questions like "who owned this service during the incident in November?" require a
history. The same pattern applies: `service_ownership_history` records every team assignment
change with a `changed_at` timestamp and the IDs of the previous and new team.

This matters for incident retrospectives, compliance audits, and understanding architectural
evolution. "When did the platform team take over the auth service?" is a query, not a memory
exercise.

**The JSONB snapshot trade-off**

Storing a full JSONB snapshot per change avoids schema coupling between the history table and
the current service record. When the service table gains a new column, old history rows still
contain valid snapshots of the previous shape. Migrations don't break history.

The cost: JSONB snapshots are larger than column-level diffs. For a service catalog at realistic
scale (hundreds of services, changes measured in dozens per day), this is not a performance
concern. The history table has a GIN index on `snapshot` for JSONB queries and a composite
index on `(service_id, changed_at)` for point-in-time lookups.

**Why these decisions age well**

Adding `tenant_id` to a table after launch requires a migration that backfills every existing
row. In a live multi-tenant database, that's a table lock or a shadow-table migration — painful,
risky, and expensive. Adding it first costs one column per table and zero production risk.

Similarly, adding a history table after engineers start asking "what did this look like last
month?" requires backfilling from external sources (logs, backups, memory). Adding it on day one
means those questions are always answerable.

Both decisions look like overhead until the day they're load-bearing.
